# 双指平移：硬件触摸板为什么能做到，我们怎么逼近

> 2026-11-01 实测记录。所有数字来自本机采集（`tests/real_pan_capture.py` / `tests/pan_msg_probe.py`），
> 不是推断。凡是推断的地方会标【推断】。

## 1. 要回答的问题

真机触摸板上做双指 pan 时：**指针不分裂、指针不被拖走、物理鼠标还能同时用**。
我们用自己的触摸注入（`CreateSyntheticPointerDevice` + `InjectSyntheticPointerInput`，`PT_TOUCH`）做 pan 时：
指针会被系统「提升」到触点、光标被隐藏、鼠标一动就看到「两个位置的指针」。为什么？

## 2. 采集方法

| 轮次 | 脚本 | 采什么 |
|---|---|---|
| 第 1 轮 | `tests/real_pan_capture.py` | 光标位置+可见性（5ms）、低级鼠标钩子每条事件（含 `LLMHF_INJECTED`）、前台窗口、Raw Input 设备级计数 |
| 第 2 轮 | `tests/pan_msg_probe.py` | 自建窗口直接收消息：A=真触摸板 pan / B=我们的触摸注入 / C=我们的滚轮，同一窗口三轮对照 |

## 3. 结果 A：真触摸板 pan 期间，光标通道完全没被碰

45 秒采集，用户在 OneNote 上做 pan，同时移动物理鼠标：

| 指标 | 实测 |
|---|---|
| 光标位置变化采样 | **1547 次** |
| 其中「找不到对应物理鼠标事件」的 | **0 次**（±15ms、坐标误差 ≤12px 全部对上） |
| 光标可见性翻转 | **1 次**（只在 t=0 记录初值，全程 `CURSOR_SHOWING=1`，**从未被隐藏**） |
| 鼠标事件 | 2486 条，**全部 `flags=0`（物理）**，0 条 `INJECTED` |

⇒ 硬件那条路上，pan 一次都没有写过光标位置，也没有触发系统的「触摸接触」状态。

## 4. 结果 B：应用收到的消息（同一窗口三轮对照）

| 阶段 | WM_POINTER | WM_GESTURE | 纵向 WHEEL | 横向 HWHEEL | 光标副作用 |
|---|---|---|---|---|---|
| A 真触摸板 pan（25s） | 392 | 81 | 6 条，全是 ±120 | 44 条，每条约 7~14 | **无** |
| B 我们·触摸注入（8s） | 1731 | 845 | 几乎为 0 | 2 条 | 隐藏 + 提升 + 光标被拖 |
| C 我们·滚轮（8s） | 2 | 0 | 306 条（1~3/条） | 384 条（2~3/条） | **无** |

关键差别不在「有没有 WM_GESTURE / WM_POINTER」（A 和 B 都有），而在**输入源的类型**：

- 触摸板是**相对设备**（`PT_TOUCHPAD`）：pan 只是「两个手指在板子上相对移动」，
  系统把它翻成滚轮/手势消息，**从不产生屏幕上的触摸接触点** → 不需要隐藏光标，也没有「触摸提升」。
- 我们是 `PT_TOUCH`（**屏幕绝对坐标的接触点**）：系统认为有一根手指按在屏幕上 →
  按触摸屏规则处理：隐藏光标、把光标「提升」到触点、给前台发 `WM_POINTER`。
- 想在用户态直接合成触摸板输入**做不到**：`CreateSyntheticPointerDevice` 只支持
  `PT_TOUCH` / `PT_PEN`，`PT_TOUCHPAD` 一律 `err=87`（多轮复现）。要真做到「设备级」只有写 HID 驱动。

【推断】A 里出现的 `WM_POINTER/WM_GESTURE` 是触摸板栈投递给窗口的**手势通知**，
不是屏幕接触——因为同一时间段光标可见性一次都没翻转，与 B 的「接触」语义不同。

## 5. 我们据此做的模拟（v6）

既然**通道**不能换（CTRL/滚轮不能接受、HID 驱动超出范围），那就把「位置语义」做到与硬件一致：

**规则：pan 期间指针位置 = pan 起点 + 用户物理鼠标在这段时间里走掉的净位移。**
- 起点 = 进入 pan 那一刻的 `GetCursorPos()`；
- 每来一条**物理**鼠标 `WM_MOUSEMOVE`（`LLMHF_INJECTED==0`），就把「事件坐标 − 我们上次写回的位置」
  累加进偏移量。基准必须是**我们上次写回的位置**，不能用上一个事件坐标
  （光标被我们每帧钉住，两次事件的绝对坐标相减会被抹平 —— 这个坑实测踩过，位移记成 0）；
- 每一帧 + 每 8ms 都 `SetCursorPos(起点 + 偏移)`：
  系统刚把光标「提升」到触点也一样被覆盖 → 指针不会跳到手指上；
- 单次位移 >1500px 才当异常丢弃（快速甩鼠标 8 米奇就能走 70px，阈值小了会把正常甩动误杀）。

实测（`tests/pan_mouse_follow.py`）：

| 断言 | 结果 |
|---|---|
| pan 期间不动鼠标，指针位置恒定 | 偏离 **0px** |
| pan 期间推 5×8 米奇 → 指针跟着走 | **+70px**（无 pan 对照 +67px，误差 3px） |
| 快速甩 180 米奇 | **+607px**（没被阈值误杀） |
| 抬手后不被拽回 | 漂移 **0px** |
| pan 期间鼠标是否被吃 / 翻倍 | 无（70 vs 67） |

`tests/pan_mouse_together.py`：A 不动鼠标 0px；B 边 pan 边推鼠标 → 指针 +183px（跟着走），
日志「用户动鼠标 11 次 / 单次最大偏离 14px」说明宿主确实在跟系统的提升抢位置。

## 6. 仍然存在的差异（必须承认）

1. **pan 期间系统仍然会隐藏光标**（接触期间 `CURSOR_SHOWING=0`），鼠标一动立刻恢复显示。
   这是合成触摸的固有副作用，只能靠换通道（滚轮/HID 驱动）消除，用户态 API 无法阻止。
2. `WM_POINTER/WM_GESTURE` 依然会投递给前台窗口（B 轮 1731/845 条），
   个别应用可能把它们当成触摸手势处理（例如绘图应用把触点当笔）。滚轮通道没有这个问题。

## 7. 结论一句话

硬件之所以「两不误」，是因为它走的是**相对设备通道**，从来没产生过屏幕接触；
我们在用户态只能用**绝对触摸**合成，所以必须自己把「接触带来的光标副作用」一帧一帧抵消掉：
**位置 = 起点 + 鼠标位移**，这才同时满足「指针不跳触点」「鼠标照常能用」「松手不拽回」。
