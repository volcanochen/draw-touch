# 触摸板手感调优全记录

> 目标只有一句话：**让手机当触摸板时，手感接近一台高端笔记本触摸板**。
> 本文记录为了达到这个手感，我们在「手势判定 / 缩放通道 / 触觉反馈」上做的每一处算法取舍与踩过的坑。
> 时间跨度：2026-10-29 ~ 2026-10-30，对应版本 v1.3.3 ~ v1.3.8。

---

## 0. 先说结论：高端触摸板「好摸」的四个特征

真实触摸板（尤其是 Mac / 高端 Windows 精密触摸板）之所以顺滑，靠的是这四点：

| 特征 | 具体表现 |
|---|---|
| **零死区的过程** | 手势一旦被识别，之后就是 1:1 跟手，手指动 0.5px 画面对应动 0.5px |
| **手势不被抢** | 捏合就是捏合，中途绝不因为手指偏移而变成滚动/拖选 |
| **方向不打架** | 横滑只横滚、竖滑只竖滚、斜滑双轴同时滚，且**不会滑到一半被拽成单轴** |
| **停手即静止** | 手指按住不动 → 画面完全不动、不重排；抬手才「定稿」变清晰 |

我们下面所有改动，都是围绕这四点展开的。

## 1. 架构前提：手机是「翻译官」，PC 是「演员」

要调手感，先搞清楚数据是怎么流的：

```
[手机] 触摸事件 → 手势判定（本文主角）→ 语义指令（13 字节帧）
                                              ↓ TCP
[PC]  解析语义指令 → 现场合成触摸/滚轮输入 → 注入 Windows
```

关键点：**手机上跑的是判定，PC 上跑的是执行**。网线上传的是「捏合了 ×1.03」这种语义，
不是原始触点坐标。所以手感问题要么出在判定（手机端），要么出在执行（PC 端），
定位时先分清是哪一端——本文每个问题都标了端。

> 详细的协议栈、输入栈图解见 `docs/触摸板技术解析.md` 与 `docs/全链路数值流程图.svg`。

## 2. 缩放：从「Ctrl+滚轮」升级到「真实双指触摸流」

### 2.1 背景：为什么以前是卡顿的

最早的缩放走 `Ctrl + 滚轮`，抓包真实触摸板发现行为完全不同：

| | 真实触摸板 | 旧的 Ctrl+滚轮 |
|---|---|---|
| 消息 | 真正的双指触摸流 | `Ctrl↓ → WM_MOUSEWHEEL ±120 → Ctrl↑` |
| 缩放中 | 画面带模糊、不重排 | 每滚一格就重排一次 |
| 停手 | 零消息，画面完全静止 | 定时重排 |

OneNote 这类「触摸板感知」应用对两种通道的处理完全不同——滚轮通道无法复刻手感。

### 2.2 关键突破：合成指针注入可用

`InjectTouchInput` 在新版 Windows 上已损坏（社区共识：任何参数永远返回 `err=87`）。
我们换成 `CreateSyntheticPointerDevice(PT_TOUCH)` + `InjectSyntheticPointerInput`：

```
CreateSyntheticPointerDevice(PT_TOUCH, maxCount=2, feedback=NONE)
    → 预注入帧（flags=0，复位设备状态）
    → 双指同帧 DOWN
    → UPDATE × N（跨度变化 = 缩放量）
    → UP（抬手定稿）
```

**踩过的坑（值得记住）**：

1. **`POINTER_TYPE_INFO` 结构体布局**：正确布局是 `uint type(偏移0) + 4 字节填充 + POINTER_TOUCH_INFO(偏移8)`。
   我们最初写成「完整 POINTER_INFO + 完整 TOUCH_INFO」并列，封送出垃圾数据 → 全部 87。
   **这一个 bug 让我们一度误判成「系统封禁了合成指针注入」**，绕了很大弯路。
2. **PT_TOUCHPAD(0xFE) 不是合法类型**，`CreateSyntheticPointerDevice` 只接受 PT_TOUCH / PT_PEN。
3. **可视化的两个白圈**：反馈模式传 `INDIRECT(2)` 时 Windows 会画出触摸圆环。
   改 `NONE(3)` 后消失（winuser.h：DEFAULT=1 / INDIRECT=2 / NONE=3），已实测注入不受影响。

### 2.3 停手不刷新：60ms keep-alive

官方文档：相邻注入帧间隔 >100ms 时触点会被判「过期」取消（应用收到手势终结 → 重排）。
真实触摸板手停时硬件仍以 ≥125Hz 上报**坐标不变**的帧。

我们用 **60ms 同坐标 UPDATE 帧**模仿：应用看到「活跃但零位移」的手势 → 不刷新、不重排。
抬手时才发 UP，此刻应用定稿变清晰。

## 3. 缩放灵敏度：死区只用于「激活」，不用于「过程」

用户明确规格：

> 只有激活的条件有死区的作用；当开始缩放状态了，死区就不存在了，不会因为小的移动就不响应。

### 3.1 错误做法（v1.3.3 之前）：逐帧丢弃

```kotlin
val factor = span / tpLastSpan          // 基准 = 上一帧跨度
if (abs(factor - 1f) > 0.005f) dispatchPinch(factor)   // 小于 0.5% 就丢弃
```

问题：基准每帧无条件刷新，被丢弃的微小变化**永久丢失**。慢速小幅捏合每帧都掉在死区里 → 手感发木。

### 3.2 中间做法（v1.3.4）：累加式

改成「上次**真正发出**的跨度」做基准 → 微小变化会累加。
仍然不合规格（过程里还是有过滤），被推翻。

### 3.3 最终做法（v1.3.5）：过程内零过滤

```kotlin
val factor = span / tpLastSpan          // 相对上一帧，逐帧相乘 = 总变化
if (factor != 1f) dispatchPinch(g2Pinch, factor)   // 只要跨度变了就发
```

- 用「上一帧」做基准：逐帧相对量**相乘即总变化**，既不丢位移也不累积漂移
- 死区只剩**激活判定**：两指都要有累计位移（≥3dp）+ 必须反向运动（点积 < 0）+ 150ms 启动窗口

## 4. 缩放「卡住放不大」：PC 端两处硬伤

现象：缩小正常，缩小后再放大很容易卡住、放不大。**不是丢数据**——日志显示每帧都在发。

### 4.1 硬伤一：跨度用了 `int`（致命）

```csharp
int ns = (int)Math.Clamp(_tzSpan * factor, TZ_MIN_SPAN, TZ_MAX_SPAN);   // ← 元凶
```

`24 × 1.01 = 24.24 → 24`。每帧乘法基数都是整数，微小增量**永远累积不起来**。
缩到最小跨度后，单帧必须 `factor ≥ 1/24 ≈ 4.2%` 才能跳 1 像素，
而实际每帧 factor 只有 1%~2%（日志实测）→ **全部无效，彻底卡死**。

修复：跨度改 `double`，只在注入那一刻取整：

```csharp
private static double _tzSpan;                       // 浮点累积
int px = (int)Math.Round(cx - span);                 // 注入时才取整
```

### 4.2 硬伤二：上下限太窄

原 `MIN=24 / MAX=600`：从基准 90 出发只能缩到 27%，手指间距稍一变化就触底。
触底后继续捏拢的量被 clamp 丢弃，反向张开得先把丢失的量补回来。

修复：`MIN=12`（可缩 7.5 倍）/ `MAX=900`（可放大 10 倍），
并加**屏幕边界约束**（两指水平排布，只需保证 x 不出虚拟屏幕）：

```csharp
_tzMaxSpan = Math.Min(TZ_MAX_SPAN, Math.Min(cx - vs.Left, vs.Right - cx) - TZ_EDGE_MARGIN);
```

诊断增强：捏合结束日志带「最终跨度」，触界时记一条 warn。

## 5. 滚动方向锁：三态 + 只判一次（但要判对）

用户规格：明显横 → 只横滚；明显竖 → 只竖滚；斜向 → 双轴同时滚，且**激活斜向后一直全方向**。

### 5.1 初版 bug：斜滑滑一小段就被锁成单轴

`AXIS_FREE(0)` 同时表示「还没判定」和「判成斜向」，代码写成 `if (axis == 0) 重新判定`
→ 斜滑时手指稍微偏向某轴就永久锁死。

修复：新增 `decideAxisOrNull()`，**把「还不能判定」（null）和「判成斜向」（AXIS_FREE）区分开**，
判定只做一次（含斜向）。

### 5.2 副作用：横向、斜向都用不了

因为判定用的是「从手势开始的累计位移」+ 门槛仅 10dp —— 起手 150ms 时一点方向噪声
（手指落下常带轻微下滑）就把它锁成竖轴并永久记住。

修复：**滑动窗口**。取最近 6 帧的质心净位移（`pushRecent()`），判的是「当前真正在往哪滑」。

### 5.3 再修：竖向锁不住（横向锁得住）

门槛放在「窗口净位移 ≥ 24dp」上，滑得稍慢就永远达不到 → 停在「未判定」（= 双轴透传）。

修复：**时机与方向分离**：

| 职责 | 依据 | 阈值 |
|---|---|---|
| 何时判定 | 累计质心位移 | `SCROLL_AXIS_MIN_DP = 24dp` |
| 判什么方向 | 最近 6 帧净位移 | `SCROLL_WINDOW_MIN_DP = 8dp` |

同时把方向偏置 `bias` 从 2.0 收到 **1.7**：
竖滑时手指横向摆幅相对更大，2.0 容易被判成斜向（这就是「横向锁得住、竖向锁不住」的另一半原因）。
1.7 仍保留 30°~60° 为斜向窗口，45° 斜滑照旧不锁。

### 5.4 锁错了能回来

已锁单轴后，若最近窗口**明确指向另一轴**（门槛 30dp、bias 3.0）允许改判一次。
斜向 `AXIS_FREE` 不参与改判（改判要求新方向是明确单轴），所以**激活斜向后依然一路全方向**。

## 6. 捏合判定：不靠「跨度阈值」，靠「反向运动」

旧逻辑 `PinchDeadZone`：跨度相对变化 >15% 且绝对变化 >6dp 才判捏合。
问题是双指靠得近时 15% 才几个像素，抖一下就误判成捏合，把双指滑动抢走。

新判定（v1.3.3 起）：

```kotlin
fun opposing(ax, ay, bx, by, minPx): Boolean {
    if (hypot(ax, ay) < minPx || hypot(bx, by) < minPx) return false
    return ax * bx + ay * by < 0f        // 向量点积为负 = 反向
}
```

- 幅度不必对称（一指动 20px、另一指动 5px 也算）
- 反向运动时质心几乎不动 → 与「质心位移」驱动的滚动判定天然不打架
- 判成捏合后**锁存**：本序列只看间距，不再回退到滚动/移动（用户规格：缩放中不应有任何移动指令）

## 7. 触觉反馈（v1.3.8 起，v1.4.0 增强）

统一的 `Haptics` 模块（Android `VibrationEffect`），原则是**轻、短、有区分**：

| 场景 | 反馈 | 时长 / 强度基准 |
|---|---|---|
| 鼠标点击（单/双击、左中右键） | 短促的「哒」 | 18ms / 150 |
| 手势被识别（捏合 / 滚动 / 单指跟随） | 确认感 | 16ms / 175 |
| 多指滑动动作（音量、任务切换…） | 稍重 | 22ms / 195 |
| 滚动过程中（双指滑动 + 右侧虚拟滚轮条） | 细震，**45ms 节流**（不会变成嗡嗡声） | 9ms / 105 |
| 双击按住拖动 开始 / 结束 | 开始重、结束轻 | 24ms/200 · 10ms/110 |
| 重按按下 / 松开 | **非对称**：按下重、松开轻短 | 28ms/255 · 10ms/120 |

右侧虚拟滚轮条与双指滚动**共用同一套反馈**（滑动中 + 无极惯性滚动期间都有细震），
滚轮条双击切换「普通/无极滚动」也给一次确认震动。

### 7.1 强度可调 + 覆盖系统限制

Android 12+ 的系统设置里有「触摸反馈强度 / 震动强度」滑条，系统会按那个比例**缩放**
我们请求的震动幅度（`Settings.System.HAPTIC_FEEDBACK_INTENSITY`）——用户把系统那条拉到最低，
我们再怎么加码也上不去，这是「明明写了 255 却几乎没感觉」的根因。

绕开的办法是**换通道**：

| 通道 | AudioAttributes usage | 受系统触觉强度缩放 |
|---|---|---|
| 默认 | `USAGE_ASSISTANCE_SONIFICATION` | **是** |
| 强制 | `USAGE_ALARM`（闹钟/提醒通道，有独立音量档） | **否** |

所以设置页给两个旋钮：

- **震动强度 %**（0~200%）：整体倍率，`强度 = 基准 × 倍率`（1~255 封顶），
  每次调整立刻震一下，让你当场听到新强度
- **覆盖系统震动强度限制**：打开即切到 `USAGE_ALARM` 通道，绕开系统缩放

prefs：`hapticStrength` / `hapticForce`（另有总开关 `hapticsOn`）。

## 8. 重按 = 按下左键（力触控拖动）

行为：移动途中用力按 → 按下左键 + 重震动，继续移动即拖选/拖拽；
力度回落 → 松开左键 + 轻短震动。抬手、手指数变化都会补发抬起，杜绝「左键卡住」。

### 8.1 两条「用力」通道

Android 的 `MotionEvent` 有两条可能表达「用力」的通道：

| 通道 | API | 本机实测 |
|---|---|---|
| **压力** | `getPressure(idx)` | **恒为 1.00** → 无真实压感，本机判死 |
| **接触面积** | `getTouchMajor(idx)` / `getTouchMinor(idx)` | **驱动有上报**（`ABS_MT_TOUCH_MAJOR/MINOR`，0~255） |

物理原理：手指按得越重，**电容椭圆的投影面积越大**。
驱动的 `ABS_MT_TOUCH_MAJOR` 就是接触椭圆的长轴，所以这条通道是存在的 ——
只是 Android 把它包装成了「触摸面积」而不是「力度」，很少有人拿它做重按。

### 8.2 判据的根本转向：判「变化量」，不判「绝对水平」（v1.4.6）

不同厂商的 `touchMajor` **单位不一样**（0.1mm、原始码值都可能出现），
而且接触面积还会随手指角度/滚动变化 —— 写死绝对阈值必然翻车。
所以判据必须是**相对量**。

但 v1.4.4 / v1.4.5 的「相对」做错了对象：

```
v1.4.4：触发 ⇔ size ≥ (手势全程最小值) × 1.1
v1.4.5：触发 ⇔ size ≥ (手势开头 10 帧的冻结基线) × 2.0
```

两者的参照物都是**一个固定的、手势开头就定下来的值**。
这在触摸板场景下**根本不成立** ——
触摸板的用法就是「**手指压着滑**」，手指落下时你本来就在用力，
开头那几帧的接触面积已经偏大。基线偏高 → 后面再怎么加力也够不到固定倍数。

- v1.4.4（×1.1）：基线偏高时反而更容易触发 → 用户反馈「**我一按就触发了**」
- v1.4.5（×2.0）：同样的病 → 用户反馈「**又太严苛了**」

用户点破的关键是：**「要识别按压的时候的变化，当有一定程度变化（相对值）就识别，
而不是绝对值。」**

正确模型 —— 参照物必须是**跟着手指走的「近期静息水平」**：

```
近期静息水平 rest = 最近 30 帧接触面积的 P20（滑动窗口，跟着手指走）
重按 ：size ≥ rest × (1 + 涨幅阈值)      （默认 +30%）
松开 ：size ≤ rest × (1 - 回落阈值)      （默认 -12%，滞回）
```

这才是物理上真正在变的东西：**一次按压动作中，手指接触面变大了多少**。
而且：
- 你压着滑 → 静息水平本来就高 → 阈值自动跟着抬高 → 不会误报
- 你在滑的过程中**额外加力** → 面积相对近期水平跳升 → 立刻识别

### 8.3 阈值 30% 的实测依据（2026-10-30 采集 461 个接触样本）

采集方式：`getevent -lt /dev/input/event9`（`sec_touchscreen`），
让用户依次做「轻触 / 普通按 / 用力按 / 压着滑 / 滑动中加力 / 逐渐加力」6 组动作。
面积取 `sqrt(TOUCH_MAJOR × TOUCH_MINOR)`，再做 EMA(0.25) 平滑。

| 观测项 | 实测值 |
|---|---|
| **采样率** | **≈41Hz**（中位间隔 24.3ms，**不是 60Hz**） |
| 静息（轻触 / 压着滑）面积 | ≈ 9.5 ~ 11.5 |
| 加力时峰值面积 | ≈ 16 ~ 21 |
| 涨幅 p25 / p50 / p75 / p90 | **-1% / +8% / +30% / +52%** |
| 涨幅 p99 | +65% |

逐帧看（`tools/analyze_touch_detail.py` 的输出）：

```
静息段：  -11 +10 +9 +13 +15 +15 +19 +27 +22 +23      ← 全部在 ±10% 内（偶发 +27%）
加力段：  +21 +43 +54 +59 +61 +52 +44 +30 +20        ← 连续一段 +39%~+68%
          +41 +51 +56 +59 +60 +65 +64 +68 +48 +33
```

所以 **+30% 卡在两者之间，两头都有余量**。

**两个参数也是数据定的：**

| 参数 | 值 | 依据 |
|---|---|---|
| 静息窗口 | 30 帧（≈0.73s @41Hz） | 要覆盖「滑过去再回来」的完整过程 |
| **确认帧数** | **3 帧**（≈73ms） | 实测**最短的一次加力只维持 3 帧** → 要 4 帧会漏掉「快速按一下」这种最常见操作 |

> 「确认帧数」这一条如果按 60Hz 直觉定成 4 帧（≈66ms）看着更稳，
> 但本机实测采样率只有 41Hz，且快速加力只有 3 帧 —— **4 帧会漏**。
> 阈值和帧数都必须按实测来，不能拍脑袋。

### 8.4 通道仲裁 + 防误触

`PressSignal` 自动挑通道：**压力可用就用压力，否则退化到接触面积**。

面积通道还有一道**启用条件**：必须先观察到面积变化超过 3%
（`areaMinVariation`）才会启用。否则手指轻微晃动带来的 1~2% 波动
会把闸门打开 → 走路时误判重按 → 左键乱按。

滞回（松开门槛低于按下门槛）避免在阈值附近反复触发。

### 8.5 踩过的坑（一）：基线初值必须是 +∞

`sizeMin` 初始为 0、而更新条件是「更小才更新」→ **它永远停在 0**
→ 基线 = 0 → 闸门一开就是「重按」→ 手指一碰屏幕就按下左键。

单测当场抓到的（`面积轻微抖动不会误判重按` 失败）。
修法：初值用 `Float.MAX_VALUE` 表示「还没有样本」。
**凡是「取最小值」的累加器，初值都不能是 0** —— 同类 bug 一条龙。

### 8.6 踩过的坑（二）：v1.4.5 收紧判定（用户实测「一按就触发」）

用户反馈：**「重按的判断要再严苛一点，因为现在我一按就触发了。」**

复查代码后找出**五个**根因，逐个修掉（不是只调阈值）：

**① 基线取 min → 取 P20 分位数**

原来基线 = 「观察到的最小接触尺寸」。手指抖一下的瞬间可能出现一个
极小值 → 基线被拉低 → 阈值跟着拉低 → 手指一碰就触发。
改用 **P20 分位数**：抗离群值，又比平均值灵敏。

**② 基线「全程最小值」→「开头窗口内冻结」**

原来基线取**全程**最小值 → 手势越往后，手指偶尔轻一点，
基线就一路下探 → **越用越敏感**。
改成：只看手势**开头**的窗口（跳过落下瞬态前 2 帧 + 取 10 帧），
算完就**冻结**。

**③ 压力通道的初值坑**

`pressureMax` 初值若为 1f，则**压力恒为 0.95** 的机器会被算成
「变化 0.05」→ 误判有压感 → `0.95 > 按下阈值 0.55` → 一按就触发。
初值改为 `+∞ / 0`，变化量才算真实。

**④ 伪压感守卫（本机之外的机器的隐患）**

伪压感机器常年报 `0.9~1.0`：变化量看着够，但**全程都在按下阈值之上**，
等于永远处于「按住」状态，一碰就误触。
所以加一条守卫：**必须存在低于按下阈值的轻触样本**，否则压力通道判死。
同时把「有压感」的判定门槛从 `0.03` 提到 `0.15`，排除小幅噪声。

**⑤ 持续确认 + 滞回**

必须**连续**若干帧超过阈值才判重按。
瞬时尖峰、以及阈值附近的来回穿越都不再误触
（实测曾 8 秒内反复 DOWN/UP 8 次）。

> ①②这两条在 v1.4.6 里被**换了个方向**：不是「把基线冻结得更死」，
> 而是「**让参照物跟着手指走**」（见 8.2）。
> 冻结只能防「越用越敏感」，但治不了「落下就带着力 → 永远触发不了」。

  否则管道缓冲会让你以为「没数据」。

### 8.8 v1.4.7：三个硬伤，全是实测挖出来的

v1.4.6 把判据换成了「相对静息水平涨了多少」，方向对了，但**静态地看公式没问题，
一放到真实曲线上跑就三个硬伤**。这一版每个改动都对应一个**实测出来的失败**。

> 下面所有数字都来自 `tools/press_search.py` 在**真实采集曲线 + 合成场景集**上的
> 全参数搜索（10368 组组合），评分函数是「同时满足 9 条性质」。
> 脚本可复现：`python tools/press_search.py tools/touch_capture.log`

#### 硬伤一：落指瞬态把静息水平拉到极低 → 每次触摸都误触发，而且按住不放

实测：手指刚落下时，接触面积从「几乎没接触」长到「压实」，
**最长 45 帧（≈1.1s）**，这段是**上冲**。
v1.4.6 把开头几帧直接当静息水平 → 参考值低到 **7.4** → 阈值只有 **9.3**
→ **第 15 帧就误触发**，而释放线是「低于 7.4×0.88」再也够不着
→ 按钮一路按到抬手，**实测按住 679 帧 = 16.6 秒**。

> 真正的根因不是「阈值太小」，而是**开头 4 帧没有历史可比**：
> 趋势守卫在这 4 帧里无法判断「是否在上涨」，于是把它们（恰好是面积最小的几帧）
> 当成了正常样本喂进静息窗口。

修法 —— **趋势守卫**：只把「相比 4 帧前没有在上涨」的帧喂给静息窗口；
**开头 4 帧一律当作上冲**。落指瞬态、加力过程都污染不了静息水平了。

#### 硬伤二：一次加力要 0.5~1 秒才长出来，会把静息水平自己顶上去 → 越按越不灵

实测：真实加力要 **20~40 帧**才长出来。
v1.4.6 的静息窗口只有 30 帧 —— 等窗口攒满，**加力已经长完了**，
参考水平追着涨上去，涨幅被吃掉 → 触发被推迟到第 **138 帧（3.4 秒）**；
在「加力后松回静息」这个最常见的场景里**完全漏掉**（一次都不触发）。

修法：窗口拉长到 **45 帧**，且**按住期间静息水平冻结**
（不被这次加力污染，也不会被长按顶高导致「按住」自己解除）。

#### 硬伤三：释放条件是「跌破静息 12%」→ 松手了按钮还按着（粘键）

用户松手时，力度只是**回到静息水平**，不是低于静息 12% → 永远够不到释放线。
实测在「长按 200 帧」场景下，v1.4.6 有 **181 帧**处于「已经判成按住、但力度其实早回落了」的状态。

修法：释放改成「**力度回落到这次加力的触发线以下**」——
触发线 = 静息水平 × (1+涨幅)，释放线 = 触发线 × 0.95。
语义直白：**按下去之后，只要松回平时的力度就算松手**。

#### 改完之后

| 指标 | v1.4.6 | v1.4.7 |
|---|---|---|
| 「加力后松回静息」 | **一次都不触发**（漏） | 触发 + 松开 ✓ |
| 「长按 200 帧」粘键帧数 | **181 帧** | **0 帧** ✓ |
| P2（静止加力）首次触发 | 第 31 帧 | **第 18 帧** ✓ |
| P4（滑动中加力）首次触发 | 第 138 帧（3.4s） | **第 63 帧（1.5s）** ✓ |
| 9 条性质全过 | ✗（5 条不过） | **✓** |

#### 已知取舍：「落下瞬间就使劲」认不出来

「手指刚落下就使劲」与「落指瞬态」在接触面积上是**同一种形状**，
物理上不可区分。本版的选择是 **宁可漏掉，也不要每次触摸都误触发**：
漏了用户再按一次；错触则每碰一下屏幕就乱按左键，功能直接不可用。
稳下来之后再加力（滑动中加力、按下拖拽）都能正常识别。

这条取舍在单测里被钉成了断言（`落下就使劲(取舍:不触发)`），
将来谁想改这个行为，必须同时改测试并说明理由。

#### 参数是怎么定的：全参数搜索 + 性质打分

不是拍脑袋调阈值，而是把「该触发/该不触发/该松开/不该粘键」写成 **9 条性质**，
再在真实曲线 + 合成场景集上做**全参数搜索**（`tools/press_search.py`，
10368 组组合），挑出同时满足全部性质的组合：

| 参数 | 取值 | 依据 |
|---|---|---|
| 静息窗口 | 45 帧（1.1s） | 要盖得住实测最长 40 帧的加力过程 |
| 就绪门槛 | 6 个**有效**样本 | 只数「非上冲」的帧 → 落指期一个都攒不到 |
| 趋势守卫 | 4 帧 / 3% | 4 帧是 EMA 后还能看出方向的最短跨度；3% 远大于噪声(1~2%)、远小于加力斜率(6%/帧) |
| 分位数 | P20 | 抗离群低值，比 min 稳 |
| 确认帧数 | 3 | 实测最短加力仅 3 帧 |
| 阈值 | 30% | 静息段全在 ±10%（偶发 +27%），加力段连续 +39%~+68% |
| 释放 | 触发线 × 0.95 | 松回平时力度就能松，同时留 25% 滞回带防横跳 |

### 8.9 v1.4.8：把旋钮交给你 —— 以及「怎么调都不会粘键」的兜底

用户的需求很直接：**「给我一个按压识别的开关，和调整压力识别的参数，我自己设置。」**

之前这三项（开关 / 压力阈值 / 面积涨幅）其实是有的，但埋在「触觉反馈」那一栏里，
翻两下才找得到，而且**只有一个阈值**能调。
v1.4.8 把它们拆成独立的「**按压识别（重按 = 按下左键）**」专区，四个旋钮全部开放：

| 项 | 范围 | 默认 | 含义 |
|---|---|---|---|
| **按压识别** | 开 / 关 | 开 | 总开关。关掉立刻松开左键，不残留 |
| **触发阈值(面积涨幅)** | 10% ~ 120% | 30% | 比平时的力度高多少算「按下去」 |
| **确认帧数** | 1 ~ 8 帧 | 3 | 连续超阈值几帧才认（1=最快，6=最迟钝） |
| **松开余量** | 0% ~ 15% | 5% | 力度要比触发线低这么多才算松手 |
| 压力通道阈值 | 0.05 ~ 0.95 | 0.55 | 仅**有真压感**的机器生效（本机无压感） |

外加「**查看当前识别状态**」：显示当前通道、静息水平、**触发线 / 松开线**、此刻涨幅 ——
调参数时不用靠体感猜该往哪拧。

#### 开放参数时才发现的一个坑：参数之间会互相放大

把释放线改成可调之后，立刻出现一个危险组合：

```
触发阈值调到 10%（涨幅小）  ×  松开余量调到 15%（余量大）
  ⇒ 释放线 = 静息 × 1.10 × 0.85 = 静息 × 0.935  ← 掉到静息水平以下
```

而用户松手时，力度只是**回到静息水平附近**（实测静息 9.5~11.5，
而参考水平取的是 P20，比均值还低一点）——
释放线一旦低于静息水平，**永远够不到 → 粘键**。
这就是 v1.4.6 的硬伤③，换个姿势又回来了。

**修法：释放线钳制在「静息水平 × 1.05」以上。**
这样无论用户怎么拧两个旋钮的组合，释放线都高过「松手后能达到的水平」→ 不会粘键。
默认参数下这个钳制**不生效**（触发线 × 0.95 远高于 1.05 倍静息），
所以 v1.4.7 的行为**一字未改**（单测 `默认参数下松开线就是触发线的九五折` 钉死了这一点）。

> 这条和第 4 条（叠加的死区会互相放大）是同一类错误的两个方向：
> 一次位移要过几道闸门，每道都在吃位移；**两个旋钮的组合也可能互相破坏**。
> 开放给用户的参数，必须先算清楚「极端组合」的后果。

#### 顺带修正的一处测试建模错误

单测「最极端参数组合也不会粘键」第一次跑是**红的**。查下来是**测试曲线建模错了**：
我把回落曲线画成「降到底就结束」，而真实场景里松手后**手还停在原地**（力度保持回到静息水平）。
少了这段保持，EMA 没有收敛机会，最后一帧的滞后就够把释放线顶过去。

改法是让曲线符合物理（回落 + 保持），而不是去改实现迁就测试 ——
因为**真实用户的松手就是「降下去并停住」**。

## 9. 指针稳定：慢速精确操作不能飘（v1.4.1 → v1.4.3）

高端触摸板的一个关键手感：**手指轻微移动时，指针几乎不动**；
但**手指真的在移动时（哪怕很慢），指针必须跟得上，位移一分不能丢**。

用户对这一条的原话最精准：

> 「**稳住和累计微小移动是两个不矛盾的事**，你看起来把微小移动给顾虑掉了，
> 我慢慢移动了好长一段距离，指针没动」

这一节记录为此付出的三代方案，以及**「稳」与「跟得上」为什么会互相打架**。

### 9.1 第一代：低通滤波（EMA）—— 走错了

第一版想用一阶低通：`filt = filt*α + raw*(1-α)`，输出 `filt - filt上一帧`。
**单测当场把它抓出来了**：匀速输入 5px/帧、50 帧共 250px，实际只输出 5px —— 指针会走不动。

原因：滤波的是「速度」，再取差值 → 稳态速度恒定 → 差值为 0。
即使改成滤波「位置」，EMA 对匀速输入也有**恒定滞后** `c = α·v/(1-α)` 像素
（α=0.92、v=5px 时滞后 46px！）：指针明显拖在手指后面，终点还固定偏一点 —— 更糟。

**结论：不要用滤波器做「稳」。**

### 9.2 第二代：速度域增益曲线 —— 方向对，但判据错

```
out = raw_delta × gain(speed)
gain:  0        微死区以下（噪声直接丢掉）
       minGain  极慢速（最低增益）
       1.0      fullSpeed 以上（快速划动 = 完全 1:1）
```

| 档位 | 微死区 | 最低增益 | 满速阈值 |
|---|---|---|---|
| 稳（默认） | 0.6px | 0.30 | 10px |
| 标准 | 0.4px | 0.55 | 7px |
| 关闭 | 0 | 1.0 | —（完全 1:1） |

**问题出在「微死区 = 0」这一格**：慢速（<0.6px/帧）的位移被**永久丢弃**。
用户慢慢划一段距离 → 指针一动不动 —— 「稳定是做到了，累计没了」。

而且这里还藏着一个**跨端耦合的坑**：

- PC 端收到的是**小数位移并会累积残量**（`_moveRemX += dx`），这样慢速移动才不会丢；
- 但反过来，**零散的小数也会被累积起来**。

于是：静止时的触摸噪声只要偶尔超过单帧死区就会被放行，
PC 端再当成真实位移累积 → 指针**慢慢爬行**（随机游走式漂移）。

**这不是增益不够，是判据不对**：用「某一帧碰巧抖没抖」去判断「手指在不在动」。

### 9.3 第三代（v1.4.2）：滑窗净位移 —— 解决了噪声，没解决慢速

```
avgSpeed = |最近 4 帧的净位移| / 帧数
```

- 噪声方向随机 → 窗口内**互相抵消** → 净位移趋 0 → 判定「没在动」；
- 真实移动方向一致 → 窗口内**互相叠加** → 正常输出。

同一段 16 帧随机噪声（幅度 0.45~0.95px，全部超过单帧死区）：

| 方案 | 噪声总输出 | 净漂移 |
|---|---|---|
| v1.4.1 单帧判死区 | 2.71 px | 随机游走，持续累积 |
| v1.4.2 滑窗净位移 | **0.29 px（1/9）** | 基本抵消 |

但**速度死区还在**（增益曲线里的 0 那 一格），所以慢速移动依旧原地不动。
真正的病根是：**用「速度」当判据 = 把「慢」等同于「静止」**，而这两件事根本不等价。

### 9.4 终版（v1.4.3）：自标定噪声闸门 —— 只判「抖动 vs 真在动」

核心转向：**不判断「有多慢」，只判断「这一下是不是抖动」。**

```
① 噪声底噪自标定：σ ≈ EMA(|Δ²位置|) / 1.954
   Δ²位置 = raw(t) - raw(t-1)
   平滑移动时 ≈ 0（速度不变）；抖动时很大（每帧独立随机）。
   —— 尺度无关：底噪 0.1px 还是 1px，估出来就是多少，不写死阈值。

② 滑窗净位移（N=8 帧）：噪声互相抵消、真移动互相叠加

③ 闸门（带滞回）：
   常规开门：样本数 ≥ 4 且 |净位移| > K·σ·√N    （K=4 → 误判率 ~1e-5）
   快速开门：|净位移| ≥ 10px                   （一次快速划动，零延迟）
   关门：|净位移| < 门槛×0.4                    （滞回，慢速时闸门不抖）

④ 输出：闸门一开就 **1:1 原样输出**（只做极轻微的速度整形）
   —— 位移一分不丢；PC 端还会把小数残量累积起来，慢速照样跟得上。
```

| 档位 | 闸门灵敏度 K | 说明 |
|---|---|---|
| **稳**（默认） | 4.0 | 噪声优先；慢速移动仍能跟上（起步慢 2~10 帧） |
| 标准 | 2.8 | 更快跟上 |
| 关闭 | — | 闸门关，完全 1:1（老手感） |

**为什么「样本数下限 ≥ 4」是必须的**：窗口没填满时门槛随 √N 变小，
两三个同号噪声样本就能骗开门（实测 net=1.81 > thr=1.30）。
加上样本数下限后，这种「同号突发」被挡住。

**为什么快速通道阈值是 10px**：真实的手指落下瞬态只有 1~3px（挡得住），
而一次快速划动单帧就有 20px 以上（必须第一帧就动，否则等于丢了 20px 的位移）。
中间不能取中间值 —— 要么丢快速划动的首帧，要么放掉落下瞬态。

**顺带去掉的一个枷锁**：指针路径上的「移动死区」（原本 8dp ≈ 15px）也一并移除。
慢速拖动时 15px 的起步死区 = 「划半秒指针还没动」，和速度死区叠加就是用户看到的那一幕。
现在抖动由噪声闸门负责，死区只管双指滚动与范围框拖动（默认也降到 3dp）。

### 9.5 实测行为（仿真 + 单测，与真机同一套算法）

| 匀速拖动速度 | 位移保留率 | 起步延迟 |
|---|---|---|
| 0.15 px/帧 | 77% | 10 帧 |
| 0.30 px/帧 | 84% | 5 帧 |
| 1.00 px/帧 | 86% | 4 帧 |
| 5.00 px/帧 | 92% | 2 帧 |
| 20.0 px/帧（快划） | **100%** | **1 帧** |

| 噪声形态 | 60 帧总输出 | 结论 |
|---|---|---|
| 白噪声 σ=0.3 | 0.00 px | 指针纹丝不动 ✓ |
| 白噪声 σ=0.6 | 0.00 px | 指针纹丝不动 ✓ |
| 手指落下瞬态 8px | 0.00 px | 被吃掉 ✓ |

保留率不是 100% 是**故意的**：闸门开门前的那几帧位移被当成「起步偏移」丢掉
（约 3~4px，合桌面约 8~12px），换来的是「静止时输出恒为 0」。
这个偏移是**固定的**，不是随时间累积的损失。

### 9.6 一个必须注意的实现细节

Android 会把一帧内的多个采样点塞进 `getHistoricalX/Y`。
如果**逐个采样点**喂平滑器，每个点的位移都很小 → 全被当噪声吃掉 → 慢速移动直接失灵。
所以必须**先把一帧内所有采样点的位移加起来，作为一个 delta 再喂**。

另外压缩是**等比例**的（x/y 同比例），不会把斜向位移掰成横/竖。

单测锁住十四条性质：静止不飘 / **慢速必须跟上** / **慢速位移不能被吃掉** /
噪声不放行成爬行 / 落下瞬态不吃掉 / 窗口未满不开门 / 快速 1:1 / 停手即停 /
方向不歪 / 高速段总位移守恒 / 斜向慢速两轴都动 / 底噪能自标定 / 档位对比 / 关闭透传。

调试时看 debug 日志里这行（每秒一条）：
`指针闸门：底噪σ=0.25px 窗口净位移=3.20px 闸门=开 样本=8`

## 10. 调优方法论（这几轮下来最好用的几条）

1. **先定位是哪一端**：手机端日志看判定（`onDebug`），PC 端日志看执行。
   手感问题 80% 靠这一步就能缩小范围。
2. **日志里带数值**：跨度、factor、axis、压力值都打出来。
   「缩小后放不大」就是靠日志里 `factor` 大多为 1.001~1.022 才定位到 int 截断。
3. **整数 vs 浮点**：凡是要累积的量（跨度、余量、死区）一律用浮点，只在最后一步取整。
4. **判一次 vs 每帧重判**：状态机类判定（方向锁、手势类型）一旦判定就锁存，
   但**判定依据必须是稳态量**（滑动窗口 / 累计量达标），不能用瞬时噪声。
5. **改完手机端必须真机验证**：单测 + 编译不算完成，必须打包安装到手机实测。
6. **手感算法一定要写单测**：本次「指针平滑」第一版（EMA 滤波速度再取差值）就是被单测当场
   抓出来的——匀速输入 250px 只输出 5px，肉眼在手机上很难立刻发现这类「越用越不对」的问题。
7. **别用滤波器做「稳」**：EMA 类低通会带来恒定滞后，指针拖在手指后面；
   「稳」要做成**判据**（只判「抖动 vs 真在动」），而不是**滤波器**。
8. **死区判据要考虑「对端怎么消费」**：PC 端为了不丢慢速位移会**累积小数残量**，
   手机端若按「单帧瞬时位移」放行噪声，噪声会被对端累积成慢速爬行。
   判「有没有真实运动」要用**滑窗净位移**（噪声互相抵消、真移动互相叠加），
   而不是看某一帧碰巧抖没抖。**两端一起看，才是完整的手感。**
9. **「稳」和「跟得上」必须分开判**（这一条最贵，学了三天）：
   任何把「慢」等同于「静止」的判据（速度死区）都会**永久丢弃慢速位移** ——
   用户原话：「稳住和累计微小移动是两个不矛盾的事」。
   正确姿势是：**只判「是不是抖动」，不判「有多慢」**；
   底噪用**二阶差分自标定**（尺度无关，不用写死阈值），
   真实移动判定用**滑窗净位移 + 样本数下限 + 快速通道 + 滞回**四件套。
10. **叠加的死区会互相放大**：指针路径上原本还有一层 8dp（≈15px）起步死区，
   和速度死区叠加，慢速拖动要划半秒指针才动。**先数清楚一帧位移要过几道闸门**，
   每一道都在吃掉位移。
11. **阈值要有量纲依据**：本机逻辑坐标 1494×593、density 1.875、
    触摸芯片原始 0~4095（量化步长 0.377px）——
    8dp = 15px = 40 个原始单位。写死阈值前先把这些换算算清楚。
12. **用户说「太灵敏」时，先查判据的每一根支柱，别只动阈值**：
    v1.4.5 收紧重按时，实际查出**五个**根因：基线取 min 会被离群值带偏、
    基线取全程最小值会「越用越敏感」、压力通道初值把伪压感判成真压感、
    伪压感全程高于阈值导致「永远按着」、缺少持续确认。
    **只把阈值从 110% 调到 200% 是治标** —— 只要有一个支柱是漏的，
    照样会误触。
13. **「变化量够」不等于「这个通道可用」**：伪压感机器压力在 0.9~1.0 之间晃，
    变化量看起来达标，但**全程都在阈值之上**，等于永远处于「按住」状态。
    判通道可用性时，除了「有没有变化」，还要问「**有没有低于阈值的那个状态**」。
14. **「取最小值」的累加器，初值不能是 0**：更新条件是「更小才更新」时，
    初值 0 会让它**永远停在 0**，下游基线恒为 0 → 闸门一开就误判。
    用 `Float.MAX_VALUE` 表示「还没有样本」。
15. **基线类参考量要用分位数，不要用 min**：min 会被单帧离群值（手抖瞬间）
    拉低；分位数（P20）抗离群，又比均值灵敏。
16. **「相对」也要选对参照物**（这条最贵，v1.4.5 → v1.4.6 学费）：
    「相对一个**冻结的历史值**」和「相对一个**跟随的当前值**」完全是两回事。
    触摸板是「手指压着滑」，落下时本就带着力 → 冻结的基线偏高 →
    再怎么加力也够不到固定倍数 → 用户连打两次回「太严苛」。
    **判「用力」要判「比最近的常态大了多少」，参照物必须跟着手指走。**
17. **阈值和帧数都要按实测来，别按直觉**：
    本机触摸采样率实测 **≈41Hz**（不是 60Hz），
    而**最短的一次加力只维持 3 帧** → 按 60Hz 直觉定「确认 4 帧」会**漏掉快速按一下**。
    `getevent` 采集 + 逐帧分析（`tools/analyze_touch_detail.py`）是唯一可靠的定参数方式。
18. **采集驱动原始数据前，先确认两个坑**：
    `getevent` 的 `BTN_TOUCH` 值是 `DOWN`/`UP` **字符串**不是 hex；
    且必须 `nohup ... &` 后台跑并重定向到文件（管道缓冲会伪装成「没数据」）。
19. **公式对不等于行为对：判据必须放到真实曲线上跑**（v1.4.7 的教训，最贵的一条）：
    v1.4.6 的判据公式读起来完全合理（「相对静息水平涨 30%」），
    但拿到真实采集曲线上跑，三个硬伤全部暴露：
    ① 落指瞬态把静息水平拉到 7.4 → **第 15 帧就误触发，按住 16.6 秒**；
    ② 一次加力要 0.5~1 秒才长出来，会把静息水平自己顶上去 → **触发推迟 3.4 秒甚至完全漏掉**；
    ③ 释放线是「跌破静息 12%」→ **松手了按钮还按着**。
    ⇒ **凡是「相对量 + 参考水平」的判据，都必须拿真实曲线跑一遍逐帧时间线**，
    看「什么时候触发、按住多久、能不能松开」，而不是只看公式。
20. **参考水平必须只吃「非上冲」的帧**（v1.4.7）：
    落指、加力都是**上冲**；把它们算进参考水平，
    参考值就会被拉到「手指刚碰屏幕那一瞬间的极小接触面」→ 阈值低到必误触发。
    **开头几帧没有历史可比，要一律当作上冲**（这是硬伤一的真正根因，
    我一开始只治了「上升趋势」却漏了「开头几帧」，结果还是第 15 帧误触发）。
21. **判据的参数用「性质打分 + 全参数搜索」定，不要手调**：
    把「该触发/该不触发/该松开/不该粘键/要够快」写成若干条性质，
    再拿真实曲线 + 合成场景集做全参数搜索（`tools/press_search.py`，
    10368 组组合），挑同时满足全部性质的。
    手调只能调「一个数」，性质能暴露「结构性问题」
    （比如 v1.4.6 的释放线，改阈值永远改不对）。
22. **有歧义的信号要显式写清取舍，并钉成断言**：
    「落下瞬间就使劲」与「落指瞬态」同形不可区分，
    本版选「宁可漏掉也别每次触摸都误触发」。
    这条取舍必须写进单测（`落下就使劲(取舍:不触发)`），
    将来谁要改，必须同时改测试并说明理由 —— 否则会被当成 bug 顺手改掉。
23. **「相对量」的参照物要选「稳态量」，还要能扛住状态切换**：
    静息水平这类参考量，一旦进入「按住」状态就必须**冻结**，
    否则一次持续几秒的加力会把参考水平顶上去 → 「按住」被自己解除 →
    长按拖拽中途弹开。这是 v1.4.7 修掉的第二个硬伤。
24. **开放给用户的参数，要先算清楚「极端组合」的后果**（v1.4.8）：
    把阈值开放出去之后，两个旋钮的**组合**会产生第三个旋钮没有的危险：
    「涨幅调小 + 释放余量调大」→ 释放线掉到静息水平以下 →
    用户松手时（力度只回到静息水平）永远够不到 → **粘键**。
    ⇒ **每个可调参数都要配一个安全兜底**（本例：释放线钳制在「静息 × 1.05」以上），
    并且**默认值下兜底不生效**（保证旧行为一字未改，单测钉死）。
    这和第 4 条（叠加的死区会互相放大）是同一类错误的两个方向：
    一次位移要过几道闸门，每道都在吃位移；**两个旋钮的组合也会互相破坏**。
25. **测试曲线要符合物理，别迁就实现**：
    「最极端参数组合不粘键」第一次跑是红的 —— 查下来是**测试曲线画错了**：
    我把回落画成「降到底就结束」，真实场景里松手后**手还停在原地**（力度保持回到静息水平），
    少了这段保持，EMA 没有收敛机会。
    修法是让曲线符合物理（回落 + 保持），而不是改实现去迁就测试 ——
    因为**用户真实的松手就是「降下去并停住」**。
26. **在 `onConfigurationChanged` 里别信 `resources.configuration`**（v1.4.9 踩过）：
    回调触发时 `resources` 拿到的可能还是**旧方向**。症状是「转屏后布局不重建」——
    横屏的两列被硬塞进竖屏，变成两条被压扁的窄列。
    修法：把回调参数 `newConfig.orientation` **显式传下去**，别在回调里再读一次全局配置。
27. **「校验」必须真的跑一遍，光搜字符串等于没校验**（v1.4.9 踩过）：
    PC 端改成单文件发布后，程序集被压缩进 exe，**明文搜版本号永远搜不到** ——
    v1.4.8 的「exe 含版本号 1.4.8: OK」其实是 `False` 被当成了通过，
    于是「包里缺 dll、双击跑不起来」这个真缺陷一路漏到了用户手上。
    修法：给程序加个 `--version`（提权逻辑之前，不弹 UAC），
    校验脚本**解压到空目录 → 实跑 → 必须输出正确版本号**。
    通用原则：**校验项要么真跑，要么就别写** —— 恒真的检查比没有检查更危险。
28. **`dotnet build` 和 `dotnet publish` 的产物不是一回事**（v1.4.9 踩过）：
    `build` 出的是 apphost（壳，依赖同目录几十个 dll 和运行时），
    `publish` + `PublishSingleFile` 出的才是**自包含单文件**（零依赖）。
    「把 exe 从 153MB 缩到 9.6MB」的直觉是错的 —— 9.6MB 那个**拷走就废**。
    体积要小，用 `EnableCompressionInSingleFile`（162MB → 72MB），
    **别用「换成 build 产物」这种假优化**。
