# 从 Raw Input 到屏幕上的指针：每一层到底发生了什么

> 这份文档回答一个问题：**「屏幕上那个指针动了」这件事，中间到底经过了哪些层？**
> 每一层能观察到什么、能改什么、改不了什么。
>
> 标记约定：
> - **【实测】**：本机（Windows 11 / 双 GPU 笔记本）用仓库里的探针跑出来的数据，可复现。
> - **【文档】**：微软公开文档描述的行为，本机未逐条验证。
> - **【未验证】**：合理推断，**不能当结论用**，需要实验确认。
>
> 写这份文档的直接原因：我们在「pan 时指针跟着手指跑」上猜错了两次，
> 两次都是因为**把某一层的现象当成了另一层的结论**。链路分清楚，才不会再看错。

---

## 0. 先看结论（时间紧只看这节）

1. **光标位置是系统的单一状态**，由 win32k 一侧维护。用户态只能读（`GetCursorPos`）和写（`SetCursorPos`），不能"参与计算"。
2. **同一个"鼠标动了"，在用户态有四个并行出口**（光标状态 / Raw Input / 低级钩子 / 窗口消息），它们是**并列**的，不是串行的。任何一路的缺失都不能推断另一路。
3. **"屏幕上看到指针" ≠ "光标位置变了"**。至少三种来源：
   - 硬件光标平面（系统画的，`BitBlt`/截图抓不到）
   - 触摸视觉/触点反馈（系统画的，触摸类输入才可能有）
   - 应用自绘的光标（比如我们的荧光笔画笔光标）
4. **本机实测**：用 `InjectSyntheticPointerInput` 注入两指触摸平移
   → 光标位置 **0px 位移**、Raw Input **0 个事件**、低级钩子 **0 个事件**、光标被系统**隐藏**。
   即：**合成触摸注入完全不经过"鼠标"这条路**。
5. **由此得到的排查铁律**：判断"指针到底动没动"，只看 `GetCursorPos` 的逐帧序列；
   判断"谁在动鼠标"，看 Raw Input 的 `hDevice`（非 0 = 真实 HID 设备）。
   不要用钩子的 `flags` 反推输入来源（我们已经在这上面翻过车，见 §5.2）。

## 2. 逐层拆解

### L0 物理设备层：相对量和绝对量是两种东西

| 设备 | 上报内容 | 说明 |
|---|---|---|
| 鼠标 | **相对**（mickeys，如 +3, -1） | 没有"绝对位置"概念 |
| 精确式触摸板 | 手指接触点（绝对）+ 多指 | 走 Digitizer 集合，不是鼠标集合 |
| 触摸屏 | 触点绝对坐标 + 接触状态 | 同上 |
| 笔 | 绝对坐标 + 压感 + 倾斜 | 同上 |

**【文档】** 这一层决定了后面所有行为的分叉：
- 相对量 → 必然经过 L2 的**加速曲线**，手指划过的距离和光标走的距离不是线性关系；
- 绝对量 → 直接落到某个坐标，但中间还可能被 L2 的"提升/promotion"改写成鼠标事件。

**【实测】** 本项目的普通指针移动没有用 `SendInput` 的相对量，而是「读当前光标位置 + `SetCursorPos` 绝对定位」，
原因就是避开加速曲线：手指比例与光标位移严格 1:1（见 `MouseControl.MoveBy`）。

---

### L1 内核驱动层：mickeys 进入系统的唯一入口

**【文档】**
- 鼠标类 HID 报文由 `mouhid.sys` 转成"鼠标输入"，交给 win32k；
- 触摸/笔/触摸板由对应驱动转成"指针输入"（pointer input），走**另一套投递路径**；
- 两条路径在 win32k 之后才可能交汇（触摸提升）。

**【实测·关键】** 两条路径不是"同一个东西的两种叫法"：

| 我们做的事 | 走哪条路 | 结果 |
|---|---|---|
| `SendInput(MOUSEEVENTF_MOVE)` | 鼠标路径 | 光标动、Raw Input 有事件、钩子有事件 |
| `InjectSyntheticPointerInput(PT_TOUCH)` | 指针路径 | 光标**不动**、Raw Input **0 事件**、钩子 **0 事件** |

> 这条差异是本项目大量困惑的根源：注入触摸**压根不产生鼠标输入**，
> 所以"用钩子检测触摸有没有把光标带跑"在原理上就不成立。

**【实测】** `CreateSyntheticPointerDevice` 本机支持情况（12 组参数全扫，`tests/TpProbe`）：

| pointerType | maxCount | 结果 |
|---|---|---|
| `PT_TOUCH` (2) | 1 / 2 / 3 / 4 | 全部 **OK** |
| `PT_PEN` (3) | 1 | **OK** |
| `PT_PEN` (3) | 2 / 3 / 4 | 全部 `err=87`（`ERROR_INVALID_PARAMETER`，笔只能单点） |
| `PT_TOUCHPAD` (5) | 1 / 2 / 3 / 4 × feedback 三种 | **全部 `err=87`** |

⇒ **本机无法创建"合成精确式触摸板"**。想走"和真实触摸板完全同一条路"这个方案，在这台机器上直接堵死（不是参数没调对，12 种组合全试过）。

### L2 win32k：光标位置在这里被算出来，也被藏起来

这一层用户态看不到，但它的产物全部可见。

#### 2.1 相对量 → 像素：加速曲线

**【文档】** `SystemParametersInfo(SPI_GETMOUSE)` 拿到三个值（阈值1、阈值2、加速开关），
系统对相对移动分段加速。所以：

```
实到像素 = f(米奇数)；f 不是线性的，且随用户的"提高指针精确度"设置变化
```

**【实测】** 无触摸接触时 +80 mickeys → 339px；注入触摸接触期间 +80 mickeys → 339px（与 338px 基线一致）。
⇒ **触摸接触不占用鼠标通道**，物理鼠标在 pan 期间可以独立工作。

#### 2.2 唯一的"光标位置"

**【文档】** 每个桌面一份光标状态（位置 + 可见标志 + 形状）。
**【实测】** `GetCursorPos` 读到的就是它；`SetCursorPos` 直接写它，**不产生** Raw Input，也**不产生**钩子事件
（我们自己钉回光标时，钩子计数不涨，就是这条）。

#### 2.3 触摸提升（touch → mouse promotion）【文档 + 未验证】

**【文档】** 触摸落在"不接受触摸"的窗口上时，系统可以把触摸**合成成鼠标输入**（点击/拖动）。
这是"用手指点老程序也能点得动"的机制。

**【未验证·重要】** 本机所有对照实验里，**这条路径一次都没触发过**：

| 组 | `hwndTarget` | 光标位移 | 钩子事件 | Raw Input |
|---|---|---|---|---|
| A | `NULL` | 0px | 0 | 0 |
| B | 前台窗口 | 0px | 0 | 0 |
| C | `WindowFromPoint(落点)` | 0px | 0 | 0 |
| D | 自建不可见窗口 | 0px | 0 | 0 |

实验条件：主屏落点 (1400,900)，落点实际窗口 `Chrome_RenderWidgetHostHWND`，每组注入 Down + 20 帧 Move + Up（`tests/RawProbe`）。

⇒ 结论只有一句能站住：**在这台机器、这个落点上，合成触摸不会被提升成鼠标**。
⇒ **不能**由此推断"别的落点（比如副屏里的 OneNote）也不会"。提升与否和落点窗口是否接受触摸有关，
而我们复现时副屏不在线（`SM_XVIRTUALSCREEN` = 0,0，虚拟桌面 3072×1920 单屏）。

#### 2.4 光标可见性：`CURSOR_SHOWING`

**【实测】** 注入触摸接触期间，系统把光标**藏起来**（`CURSORINFO.flags & 1` = 0），
且**不会自己恢复**（抬手后仍可能保持隐藏，需要外部叫醒）。
20 帧采样里 20/20 都是隐藏。

**【实测】** 藏起来的光标，`SetCursorPos` 到同一点**不能**让它重新出现；
只有"1 像素相对移动"（`mouse_event(MOVE,1,0)` 或 `SendInput`）才能点亮 —— 但这一戳会带偏位置，
所以点亮后必须再钉一次。

> 这就是本项目"平移期间要不要点亮光标"一直纠结的物理根源：
> 不点亮 → 用户觉得指针消失；点亮 → 点亮动作本身是鼠标输入，会参与光标竞争。

### L3 用户态四个出口：并列，不是串行

这是最容易搞错的一层。**它们是同一份内核输入的不同视图**，任何一路为空都不代表输入不存在。

| 出口 | API | 能看到什么 | 本机实测：注入触摸时 | 本机实测：`SendInput` 时 |
|---|---|---|---|---|
| ① 光标状态 | `GetCursorPos` / `GetCursorInfo` | **最终位置** + 是否可见 | 位置 0px 变化；可见=false | 位置按预期移动 |
| ② Raw Input | `RegisterRawInputDevices` + `WM_INPUT` | HID 原始报文，`hDevice` 区分设备 | **0 个事件** | 1 个事件，`hDevice=0`（注入标记） |
| ③ 低级钩子 | `SetWindowsHookEx(WH_MOUSE_LL)` | `MSLLHOOKSTRUCT`：坐标、`flags`、`dwExtraInfo` | **0 个事件** | 1 个事件，`flags=0x1`、`extra='TEST'` |
| ④ 窗口消息 | `WM_MOUSEMOVE` 等 | 投递给具体窗口，带 wParam 按键状态 | 无鼠标消息 | 有 |

#### 3.1 关于 Raw Input 的 `hDevice`

**【文档】** `RAWINPUTHEADER.hDevice` = 产生该输入的设备句柄；注入输入（`SendInput`）通常为 0。
**【实测】** `SendInput` 的鼠标移动 → `hDevice = 0x0`（`tests/RawProbe` 输出）。

**【未验证】** "真实物理鼠标的 `hDevice` 一定非 0" —— 这是文档说法，本机没测过（需要动手移一次鼠标并抓 Raw Input）。
**在拿真机数据之前，不要把"hDevice != 0"当成产品判据。**

#### 3.2 关于低级钩子的 `flags`

**【实测】** 我们自己的 `SendInput`（带 `dwExtraInfo='SPTB'`）→ `flags=0x1`（`LLMHF_INJECTED`）。
**【实测】** 测试脚本的 `SendInput`（带 `'TEST'`）→ `flags=0x1`。
**【实测·血案】** 用户真机 pan 期间抓到的钩子事件是 `flags=0x0 extra=0x0` —— 与**物理鼠标完全同形**，
我们的判据 `(flags & LLMHF_INJECTED) == 0 ⇒ 物理鼠标` 于是把这些事件当成"用户在用鼠标"，
每帧把锚点搬到事件坐标，**锚点被搬走 486 次**，`dev` 恒为 0，钉回逻辑一次都没触发。

⇒ **教训**：钩子的 `flags/extra` 只能用来"排除自己注入的"，**不能**用来"认定这就是物理鼠标"。
它们分不清"物理鼠标"和"系统合成的鼠标事件"。

### L4 呈现层：屏幕上亮起来的东西，可能和光标位置无关

**【文档】** 系统光标由**硬件光标平面**绘制，不进入桌面位图，所以：
- `BitBlt` 截图抓不到光标；
- `PrintWindow(PW_RENDERFULLCONTENT)` 通常也抓不到；
- 想"截图看看有几个指针"，基本不可行。

**【文档】** 触摸类输入可以带视觉反馈（触点涟漪/触摸指针），由 `CreateSyntheticPointerDevice` 的
`feedbackMode` 控制：`POINTER_FEEDBACK_DEFAULT / INDIRECT / NONE`。本项目用的是 **NONE**。

**【未验证】** "用户在 pan 时看到的第二个指针"到底属于哪一类：

| 候选 | 特征 | 怎么证伪/证实 |
|---|---|---|
| A. 系统触摸指针/触点视觉（触点位置） | 跟手指走、原点还留着一个光标 | 注入 `feedbackMode=NONE` 后仍出现 ⇒ 不是 feedback；换落点窗口是否消失 |
| B. 触摸提升后的合成鼠标指针 | 跟手指走，且 `GetCursorPos` 也会变 | 读逐帧 `GetCursorPos`：变了才是它 |
| C. 应用自绘光标（如荧光笔画笔） | 形状可辨、通常不随手指 | 关掉对应功能看是否消失 |

**判别顺序（下次遇到直接照这个来）**：
1. 先读**逐帧 `GetCursorPos`** —— 位置没变，就排除 B；
2. 再看该功能有没有自绘光标 —— 有就排除 C；
3. 剩下只能是 A（系统视觉），而 A 目前**没有公开 API 可以关闭**，只能改方案（换输入类型/换投递方式）。

## 5. 我们踩过的两个坑（写给人看，防止再犯）

### 5.1 把"位置变了"当成"用户在动鼠标"

早期用"光标位置变了"判断用户是否在用鼠标。问题：系统自己的提升/隐藏也会改位置。
结论：**位置变化不是来源证据**。

### 5.2 把"钩子 flags 干净"当成"物理鼠标"

见 §3.2。`flags=0` 的事件里既有物理鼠标，也有系统合成事件。
结论：**钩子只能排除自己注入的，不能认证外部来源**。

### 5.3 正确的取证顺序

```
现象（"指针跟手"）
  → ① 逐帧 GetCursorPos：位置变了吗？
        变了  → 在 L2 光标状态层，继续查是谁写的（Raw Input hDevice / 我们的 SetCursorPos）
        没变  → 不是光标，去 L4 呈现层找（自绘 / 系统视觉）
  → ② 只有确认"位置变了"，才去查输入来源（Raw Input / 钩子 / 我们自己的注入）
```

## 6. 还没验证的事（别当结论用）

1. 真实物理鼠标的 Raw Input `hDevice` 是否稳定非 0（需要一次真机移动 + 抓 Raw Input）。
2. 触摸提升在**副屏 OneNote** 这类落点上是否会真的发生（本机复现时副屏不在线）。
3. 用户看到的"第二个指针"属于 §2.4 表里的哪一类。
4. `PT_TOUCHPAD` 的 `err=87` 是"这台机器/这个版本不支持"，还是"任何机器都不支持合成触摸板"。
