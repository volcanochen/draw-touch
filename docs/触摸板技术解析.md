## 一、真实触摸板是怎么工作的

### 1.1 硬件层：电容感应矩阵

真实触摸板（无论笔记本内置的还是外接的）在物理上是一块**电容感应网格**：

- 板上横竖交织着电极，以很高的频率（精密触摸板要求 ≥ 125Hz，好的可达 90~180Hz 甚至更高）扫描整个平面；
- 手指靠近会改变局部电容，控制器根据行列信号的变化强度**插值出每个触点的质心坐标**，精度远高于触点物理尺寸（亚毫米级）；
- 接触面积（手指压得多实）也会改变电容总量，所以报文里通常还带 contact size / pressure。

### 1.2 系统层：Windows 精密触摸板（Precision Touchpad）

微软从 Win8.1 起定义了「精密触摸板」规范，关键点是：

1. **硬件只上报原始触点**（多点坐标 + 接触面积 + 置信度），**手势识别完全交给 Windows**。驱动不需要自己实现捏合、滚动。
2. 触点经 HID 栈进入系统后，Windows 输入合成器把它统一成**指针（Pointer）消息流**：`WM_POINTERDOWN` → 一串 `WM_POINTERUPDATE` → `WM_POINTERUP`。每个消息带 pointerId、坐标、接触矩形（rcContact）。
3. 应用拿到的是**连续的、带多指的原始指针流**，而不是翻译好的「滚动 +3 格」「缩放 1 格」。这正是手感差异的来源：
   - **位移是相对量、逐帧连续**，没有格（notch）的量化；
   - **手势的生命周期就是手指的生命周期**——两指从按下到抬起的整个期间，应用收到的是一个持续活跃的接触序列。

### 1.3 为什么真实触摸板缩放「带模糊、松手才变清晰」

前台应用（浏览器 / OneNote / 图片查看器等）对触摸捏合的处理方式是**直接操作（Direct Manipulation）**：

- 收到两指捏合的连续指针流时，应用实时地对内容做**仿射缩放**（矢量内容或位图直接拉伸），此时为了保持帧率，很多应用只做插值缩放、**不重新排版/重渲染**——观感就是「缩放模糊」；
- 直到收到 `WM_POINTERUP`（手指全部离开、手势终结），应用才判定「用户定稿了」，此时才触发重排/重绘/回流，画面瞬间变清晰；
- 手指中途停住不动时，指针流暂时没有新位移，但**手势仍然活跃**（接触点还按着），应用不会趁机定稿——所以画面静止且保持模糊，绝不会「停一下就刷新」。

一句话总结：**真实触摸板的流畅 = 高频连续相对量 + 手势生命周期与手指严格绑定**。

## 二、模拟触摸板的两大技术路线

要在 PC 上「假装」一块触摸板，只有两条本质不同的路：

### 路线 A：鼠标滚轮 / 快捷键合成（SendInput）

- 用 `SendInput` 发 `MOUSEEVENTF_WHEEL`（可叠加 Ctrl 键做缩放）。
- 滚轮是**离散格数**：一格 = 120 个 wheel delta，应用收到后立即执行一次「缩放一格」并**立刻重排刷新**。
- 优点：兼容性 100%，任何系统任何应用都认；
- 缺点：**离散跳变**，没有手势生命周期概念，应用每次都重排 → 卡顿、闪烁、伴随「居中移动」等副作用。这正是我们早期 Ctrl+滚轮方案手感差的根本原因。

### 路线 B：触摸注入（InjectTouchInput）——我们现在的方案

- Windows 提供公开 API：`InitializeTouchInjection(maxCount, feedback)` + `InjectTouchInput(count, POINTER_TOUCH_INFO[])`。
- 它把调用方进程**虚拟成一个触摸屏设备**：每次调用注入一帧（可以同时含多个触点），系统把这帧触点当成真实触摸屏数据走**同一条指针流**，前台应用收到的和真手指点屏幕完全一样。
- 双指捏合的注入方式：同时维护 pointerId=0 和 1 两个触点，一帧内左右对称地移动它们，两指间距变化 → 应用自动识别为 pinch-zoom。

**这两个 API 做了什么、站在输入栈的哪个位置：**

- `InitializeTouchInjection(maxCount, feedbackMode)`：在 win32k 输入子系统里给当前进程**注册一个「触摸输入源」名额**（分配 maxCount 个触点槽位，feedback 控制系统触摸视觉反馈）。**不装驱动、不建设备节点、不走 HID**，只是开一个用户态直通输入合成器的口子。
- `InjectTouchInput`：把一帧触点快照塞进**内核输入栈**，与真实硬件输入走**同一条队列、同一套后续处理**（win32k 指针合成 → WM_POINTER 投递 → 应用解释）。前台应用无法区分注入与真触摸。
- **位置**：绕过 HID 驱动层，在 win32k 指针合成**之前**汇入；`SendInput` 同理但走鼠标/滚轮路径（与触摸路径平行）。真实精密触摸板比注入多一层 **PTP 系统级手势合成**（HID 之后、入队之前）——注入路径没有这层，所以「这是什么手势」必须由调用方自己判定。

```
真实触摸板(HID) ─→ PTP手势合成 ─┐
真实触摸屏(HID) ────────────────┤
InjectTouchInput ───────────────┼→ 内核输入队列 → win32k指针合成 → WM_POINTER → 应用
SendInput(鼠标) ────────────────┘   (全部汇合)      (触摸→指针流)      (滚轮→滚轮消息)
```

**注入状态机（微软文档强制要求）：**

| 阶段 | pointerFlags | 说明 |
|---|---|---|
| 触点落下 | `INRANGE \| INCONTACT \| DOWN` | 开启接触 |
| 接触中移动 | `INRANGE \| INCONTACT \| UPDATE` | 每帧更新坐标 |
| 抬起 | `INRANGE \| UP` | **必须发**，否则触点永远挂着（曾经造成左键锁死事故） |

**几个关键坑（都是实测踩出来的）：**

1. **相邻两帧坐标必须变化**：完全相同坐标的 UPDATE 帧系统直接报 `err=87 (ERROR_INVALID_PARAMETER)`。之前我们把它误诊为「本机不支持触摸注入」而熔断——实际上只要跨度不变时给中心加 ±1px 交替微移就完全正常。
2. **帧内两触点必须同帧提交**：一次 `InjectTouchInput(2, arr)` 传两个 POINTER_TOUCH_INFO，frameId 相同，系统才认为是一帧多点。
3. **`historyCount` 必须为 1**（未合并历史时），0 在部分系统上被判无效参数。
4. 注入失败熔断要谨慎：连续失败 3 次才判定不支持，且失败计数在成功后归零。

### 两条路线的手感本质区别

| | 路线 A（Ctrl+滚轮） | 路线 B（触摸注入） |
|---|---|---|
| 缩放粒度 | 离散格，一格一跳 | 连续相对量，逐帧 |
| 手指停住 | 无手势概念，余量游走会造成画面乱动 | 手势保持活跃，画面静止 |
| 松手行为 | 每格都已刷新，无「定稿」 | 应用收 UP 才重排 → 模糊→清晰的定稿 |
| 应用兼容 | 全兼容 | 现代应用全支持，极老程序可能不认触摸 |

## 三、SpenTablet 的实现：手机当触摸板的全链路

### 3.1 总体架构

```
┌─────────── 手机端 (Kotlin) ───────────┐        ┌────────────── PC 端 (.NET 8) ──────────────┐
│ PenCanvasView 触摸事件                │  TCP   │ TcpPenServer 解析 TYPE_MOUSE 帧            │
│  → 双指手势状态机（捏合/滚动/跟随）    │ ─────→ │  → MOUSE_ZOOM: ①触摸注入(优先)             │
│  → 捏合: 算相对系数 factor            │  6000  │                ②Ctrl+滚轮(降级)            │
│  → MOUSE_ZOOM/MOUSE_SCROLL 帧        │        │  → MOUSE_FINGER off: EndTouchZoomIfActive  │
│  → MOUSE_FINGER 在板/离板状态帧       │        │ MouseControl: InjectTouchInput 状态机       │
└──────────────────────────────────────┘        └────────────────────────────────────────────┘
```

协议帧格式：`0x53 0x50 + type + len + payload`。触摸板动作全部走 `TYPE_MOUSE (0x07)`，payload 首字节是子命令 kind（`MOUSE_MOVE=0 … MOUSE_LEFT_DOUBLE=16`），后接两个 float（dx/dy，语义随 kind 变化）。`MOUSE_ZOOM` 的 dx 字段就是**相对缩放系数 factor**（>1 张开 / <1 捏拢）。

### 3.2 手机端：双指手势状态机（PenCanvasView.kt）

> **关键澄清：手机传的是语义指令，不是触点数据。**
> 经常被问：发给 PC 的是 `POINTER_TOUCH_INFO` 吗？是每个 pointer 的坐标吗？——都不是。
> `POINTER_TOUCH_INFO` 只存在于 PC 端内存，是 PC 收到指令后**现场合成**的。
> 手机发的是**语义指令**：「这是捏合，相对系数 ×1.03」「这是滚动，dy=35px」「这是双指点击」。
> 手势是什么、该干什么，在手机上就已经决定了。
>
> 为什么不在 PC 端算捏合系数？因为**「这是捏合还是滚动还是移动」的判定无论如何都要在某个地方做，而它只能做在有原始触点数据的那一端——手机**：
>
> 1. **PC 看不见两根手指。** 原始触点只存在于手机的触摸事件流里。要让 PC 判定，就得把两指原始坐标逐帧传过去——判定逻辑（捏合/滚动/单指跟随的消歧，即整个状态机）只是从手机搬到 PC，一点没少，还多了一层传输。
> 2. **Windows 不会替你消歧。** 就算把原始双指坐标原样注入，Windows 只把它们当「两个移动的触点」透传，应用会同时看到 pan 和 zoom 混叠：手指稍不完全平行，滚动就带出缩放抖动。真实触摸板的系统级手势合成是精密触摸板驱动栈的特权；`InjectTouchInput` 走触摸屏路径，没这层。手机端判定后发出的 factor 是**纯缩放**（只有跨度变化、中心不动），滚动是**纯滚动**——语义干净。
> 3. **相对系数才是本质信息，触点是布景。** 应用算缩放量只看**跨度的相对变化率**；PC 端的基准跨度 ±90px 是虚构的，绝对值无所谓。就算传了原始坐标，PC 最终能提取的有效信息也正是手机算的那个 factor。
> 4. **几何映射绕不开。** `InjectTouchInput` 要屏幕绝对坐标、触点不能出屏；手指在手机上的位移映射到桌面哪个虚拟区域、捏合中心放哪（= 光标位置），本来就得 PC 端重建。传原始坐标只是多一层要对齐的换算。
>
> 一句话：**手机端是手势翻译官，PC 端是手势演员**——翻译官决定这句话是什么意思，演员在系统面前把它演成一段标准、无噪声的双指触摸戏。

三态 + 一个锁存位：

- `tp2State`：0=未判定 → 1=缩放 / 2=滚动 / 3=单指跟随（光标移动）
- `tpPinchLatched`：捏合锁存，一旦判成捏合，**直到全部手指抬起前任何事件都不重置、不再发移动指令**——彻底隔离「缩放中混进光标移动」。

**判定优先级（每帧两指事件到达时）：**

1. **捏合随时可判、最优先**：`TwoFingerLogic.opposing()`——两指各自累计位移向量模都 ≥ `TP2_BOTH_MIN_DP=3dp`，且**点积 < 0**（在相反方向上运动）。点积判据的好处：不要求幅度相等（用户要求：「只要不是一个静止就算捏合」），也不要求精确共线；
2. **单指跟随 / 滚动**要等启动窗口 `TP2_FOLLOW_DELAY_MS=150ms`——给「捏合起手一指先动」留识别时间，防止把质心位移误判成滚动/移动；
3. 判成缩放后，跨度系数 `factor = span / lastSpan`，只有 `|factor-1| > PINCH_IDLE_DEADZONE=0.005` 才发帧——**手停死区**，防止停手微抖在 PC 端累积成随机游走。

**状态帧**：手指按下触摸板区域/离开时发 `MOUSE_FINGER(on/off)`——这是 PC 端精确结束捏合的信号源。

### 3.3 PC 端：缩放双路径 + keep-alive（MouseControl.cs / TcpPenServer.cs）

**MOUSE_ZOOM 到达时：**

```
① 触摸注入优先（_cfg.PinchMode != "Wheel" 且注入可用）
   UpdateTouchZoom(factor, 光标位置):
     首帧   → Down: 两触点落子 (cx±90, cy)，开启手势
     后续帧 → Move: span = clamp(span × factor, 24, 600)
              span 没变 → 中心 ±1px 交替微移（防 err=87，两帧抵消）
② 注入不可用 → 降级 Ctrl+滚轮：对数余量 _zoomNotch 累计，够一格发一格
```

**手势生命周期（对标真实触摸板的三件套）：**

| 真实触摸板行为 | 我们的对应实现 |
|---|---|
| 手指停住 → 手势仍活跃、不刷新 | `TZ_KEEPALIVE_MS=120`：手停时定时器注入 keep-alive 微移帧（坐标必变、跨度不变），应用始终看到「两指按着」 |
| 手指抬起 → UP 定稿、变清晰 | 手机 `MOUSE_FINGER off` → `EndTouchZoomIfActive()` 立即注入 `INRANGE\|UP` 帧，应用此刻才重排 |
| 异常兜底 | `TZ_SAFETY_LIFT_MS=3000`：3 秒完全无帧才强制抬手，防触点残留（曾经的左键锁死事故） |
| 系统不支持 | 连续失败 3 次熔断 → 永久降级 Ctrl+滚轮，不再刷日志 |

**语义指令 → PC 端系统调用对照（注意：没有任何一条传触点坐标）：**

| 手机端发的 kind | payload | PC 端动作 |
|---|---|---|
| `MOUSE_MOVE(0)` | 归一化位移 dx/dy | `SendInput` 鼠标相对移动（光标） |
| `MOUSE_ZOOM(6)` | 相对系数 factor | 合成两触点注入（`span×=factor`）或 Ctrl+滚轮 |
| `MOUSE_SCROLL(5)` | 滚动量 dx/dy | 像素级滚轮（非触摸注入——纯滚动不需要手势生命周期） |
| `MOUSE_FINGER(15)` | 在板/离板 | on：S Pen 让位；off：`EndTouchZoomIfActive()` 结束捏合定稿 |
| `MOUSE_LEFT_*` / 右键 / 中键等 | — | 对应鼠标按键合成 |

### 3.4 当前与真实触摸板的差距（诚实清单)

1. **接触矩形是假的**：注入的 rcContact 固定 ±3px，没有真实手指的接触面积/压力变化。对缩放手感无影响，但依赖接触面积的少数应用（如压感绘画）会感知差异。
2. **±1px jitter 理论可感知**：同坐标防 87 的微移在数学上两帧抵消，但逐帧看中心在 ±1px 摆动，极少数对亚像素敏感的应用可能察觉极轻微抖动。
3. **keep-alive 帧率 8Hz**：真实触摸板手停时也在 125Hz+ 刷新（只是位移为零）。我们的 keep-alive 是 120ms 一帧——对「保持手势活跃」这个目的足够，但不是物理等价。
4. **触摸注入 ≠ HID 驱动级设备**：注入的触摸来自「虚拟触摸屏」而非「虚拟触摸板」，系统层某些触摸板专属特性（如三指手势、边缘滑动）不会由系统自动合成。我们的做法是手机端识别手势后映射成具体动作（音量、Alt+Tab 等已是这个思路）。
5. **终极方案（未做）**：写一个虚拟 HID 精密触摸板驱动（内核级），让系统把手机当成原生 PTP 硬件——兼容性和系统合成手势都是满血，但需要驱动签名，工程量大，暂不划算。

## 附录：一次捏合的完整数值实例

场景：手机 1080×2340，PC 2560×1440，用户在 OneNote 里双指张开放大画布。

**① 手机端 · 触摸事件流（原始双指坐标，每 16ms 一帧，从不上网）**

```kotlin
MotionEvent(
  pointer0: (620.3, 815.2) px,   // 食指
  pointer1: (705.8, 830.1) px,   // 拇指
  action = MOVE                    // 两指都按在触摸板区
)
```

**② 手机端 · 状态机判定（每帧一次）**

```kotlin
tpVecA = (12.4, -3.1) px    // 食指累计位移，向右上
tpVecB = (-14.8, 2.9) px    // 拇指累计位移，向左下

TwoFingerLogic.opposing()：
  magA = 12.8 ≥ 3dp门槛 ✓
  magB = 15.1 ≥ 3dp门槛 ✓
  点积 = 12.4×(-14.8) + (-3.1)×2.9 = -192.5 < 0（反向）✓
→ 判成捏合：tp2State=1，tpPinchLatched=true（从此不再发光标移动）
```

**③ 手机端 · 相对系数 + 死区过滤**

```kotlin
span_last = 185.6 px; span_now = 191.2 px
factor = 191.2 / 185.6 = 1.0302
|1.0302-1| = 0.0302 > PINCH_IDLE_DEADZONE(0.005) ✓ 发帧
（若算出 1.003 → ≤ 死区 → 本帧丢弃，什么都不发）
```

**④ 网线上实际跑的字节（全部有效信息 = 4 字节）**

```
53 50 07 0D 06 | D8 DD 83 3F | 00 00 00 00
│  │  │  │  │    └ dx = 1.0302（float32 小端）＝相对缩放系数
│  │  │  │  └ kind = 0x06 = MOUSE_ZOOM
│  │  │  └ payload 长度 = 13
│  │  └ type = 0x07 = TYPE_MOUSE
│  └ 魔数 'P'   └ 魔数 'S'
没有坐标、没有 pointer、没有触点。
```

**⑤ PC 端 · TcpPenServer 解析**

```
kind=6 → MOUSE_ZOOM，factor=1.0302
GetCursorPos() → (1247, 633)   // 捏合中心 = 光标位置
```

**⑥ PC 端 · MouseControl 合成触点（触点在此诞生）**

```
首帧：pointerId=0 坐标(1157,633)，pointerId=1 坐标(1337,633)
      = 中心(1247,633) ± 90；rcContact ±3px
      flags = INRANGE|INCONTACT|DOWN，frameId=1；span 记 90
后续帧：span = 90×1.0302 = 92.7 → 93
      pointerId=0 (1154,633)，pointerId=1 (1340,633)
      flags = INRANGE|INCONTACT|UPDATE，frameId=7
InjectTouchInput(2, contacts) → true
```

**⑦ 系统 → 应用（应用收到的是这些）**

win32k 合成 pointer 帧 → OneNote 同帧收到两个 WM_POINTERUPDATE

**⑧ 手停（keep-alive）**

```
手机端死区滤帧 → 网线安静。

```

**⑨ 松手定稿**

```

```

**兜底支线**：第⑥步连续失败 3 次（err=87）→ 永久熔断，改走 Ctrl+滚轮：
`_zoomNotch += ln(1.0302)×10 = 0.297 格`，累计满 1 格才发 `Ctrl+滚轮 ±1` —— 离散跳变、每格刷新的老路。

## 四、一页速查

- **真实触摸板**：硬件报原始触点 → Windows 统一成 WM_POINTER 流 → 应用直接操作；流畅的根源 = 连续相对量 + 手势生命周期与手指绑定（松手才定稿）。
- **模拟路线**：SendInput 滚轮（离散、必刷新）vs InjectTouchInput 触摸注入（连续、可保持手势）——我们选后者，滚轮作降级。
- **我们的链路**：手机端状态机（opposing 向量判捏合 → 锁存隔离 → 死区滤抖）→ TCP 帧携带相对 factor → PC 端触摸注入状态机（Down/Move/Up 严格状态机 + keep-alive 手停保持 + MOUSE_FINGER off 精确结束 + 3s 兜底 + 失败熔断降级）。
- **调试入口**：PC 日志 `[TouchZoom]` 前缀（开始捏合/注入失败/捏合结束）、`[Mouse] 捏合 ×… → 触摸板真实缩放 | Ctrl+滚轮 N 格`。
