## 一、真实触摸板是怎么工作的

### 1.1 硬件层：电容感应矩阵

真实触摸板（无论笔记本内置的还是外接的）在物理上是一块**电容感应网格**：

- 板上横竖交织着电极，以很高的频率（精密触摸板要求 ≥ 125Hz，好的可达 90~180Hz 甚至更高）扫描整个平面；
- 手指靠近会改变局部电容，控制器根据行列信号的变化强度**插值出每个触点的质心坐标**，精度远高于触点物理尺寸（亚毫米级）；
- 接触面积（手指压得多实）也会改变电容总量，所以报文里通常还带 contact size / pressure。

### 1.2 系统层：Windows 精密触摸板（Precision Touchpad）

微软从 Win8.1 起定义了「精密触摸板」规范，关键点是：

1. **硬件只上报原始触点**（多点坐标 + 接触面积 + 置信度），**手势识别完全交给 Windows**。驱动不需要自己实现捏合、滚动。
2. 触点经 HID 栈进入系统后，Windows 输入合成器把它统一成**指针（Pointer）消息流**：`WM_POINTERDOWN` → 一串 `WM_POINTERUPDATE` → `WM_POINTERUP`。每个消息带 pointerId、坐标、接触矩形（rcContact）。
3. 应用拿到的是**连续的、带多指的原始指针流**，而不是翻译好的「滚动 +3 格」「缩放 1 格」。这正是手感差异的来源：
   - **位移是相对量、逐帧连续**，没有格（notch）的量化；
   - **手势的生命周期就是手指的生命周期**——两指从按下到抬起的整个期间，应用收到的是一个持续活跃的接触序列。

### 1.3 为什么真实触摸板缩放「带模糊、松手才变清晰」

前台应用（浏览器 / OneNote / 图片查看器等）对触摸捏合的处理方式是**直接操作（Direct Manipulation）**：

- 收到两指捏合的连续指针流时，应用实时地对内容做**仿射缩放**（矢量内容或位图直接拉伸），此时为了保持帧率，很多应用只做插值缩放、**不重新排版/重渲染**——观感就是「缩放模糊」；
- 直到收到 `WM_POINTERUP`（手指全部离开、手势终结），应用才判定「用户定稿了」，此时才触发重排/重绘/回流，画面瞬间变清晰；
- 手指中途停住不动时，指针流暂时没有新位移，但**手势仍然活跃**（接触点还按着），应用不会趁机定稿——所以画面静止且保持模糊，绝不会「停一下就刷新」。

一句话总结：**真实触摸板的流畅 = 高频连续相对量 + 手势生命周期与手指严格绑定**。

## 二、模拟触摸板的两大技术路线

要在 PC 上「假装」一块触摸板，只有两条本质不同的路：

### 路线 A：鼠标滚轮 / 快捷键合成（SendInput）

- 用 `SendInput` 发 `MOUSEEVENTF_WHEEL`（可叠加 Ctrl 键做缩放）。
- 滚轮是**离散格数**：一格 = 120 个 wheel delta，应用收到后立即执行一次「缩放一格」并**立刻重排刷新**。
- 优点：兼容性 100%，任何系统任何应用都认；
- 缺点：**离散跳变**，没有手势生命周期概念，应用每次都重排 → 卡顿、闪烁、伴随「居中移动」等副作用。这正是我们早期 Ctrl+滚轮方案手感差的根本原因。

### 路线 B：触摸注入（InjectTouchInput）——我们现在的方案

- Windows 提供公开 API：`InitializeTouchInjection(maxCount, feedback)` + `InjectTouchInput(count, POINTER_TOUCH_INFO[])`。
- 它把调用方进程**虚拟成一个触摸屏设备**：每次调用注入一帧（可以同时含多个触点），系统把这帧触点当成真实触摸屏数据走**同一条指针流**，前台应用收到的和真手指点屏幕完全一样。
- 双指捏合的注入方式：同时维护 pointerId=0 和 1 两个触点，一帧内左右对称地移动它们，两指间距变化 → 应用自动识别为 pinch-zoom。

**这两个 API 做了什么、站在输入栈的哪个位置：**

- `InitializeTouchInjection(maxCount, feedbackMode)`：在 win32k 输入子系统里给当前进程**注册一个「触摸输入源」名额**（分配 maxCount 个触点槽位，feedback 控制系统触摸视觉反馈）。**不装驱动、不建设备节点、不走 HID**，只是开一个用户态直通输入合成器的口子。
- `InjectTouchInput`：把一帧触点快照塞进**内核输入栈**，与真实硬件输入走**同一条队列、同一套后续处理**（win32k 指针合成 → WM_POINTER 投递 → 应用解释）。前台应用无法区分注入与真触摸。
- **位置**：绕过 HID 驱动层，在 win32k 指针合成**之前**汇入；`SendInput` 同理但走鼠标/滚轮路径（与触摸路径平行）。真实精密触摸板比注入多一层 **PTP 系统级手势合成**（HID 之后、入队之前）——注入路径没有这层，所以「这是什么手势」必须由调用方自己判定。

```
真实触摸板(HID) ─→ PTP手势合成 ─┐
真实触摸屏(HID) ────────────────┤
InjectTouchInput ───────────────┼→ 内核输入队列 → win32k指针合成 → WM_POINTER → 应用
SendInput(鼠标) ────────────────┘   (全部汇合)      (触摸→指针流)      (滚轮→滚轮消息)
```

**注入状态机（微软文档强制要求）：**

| 阶段 | pointerFlags | 说明 |
|---|---|---|
| 触点落下 | `INRANGE \| INCONTACT \| DOWN` | 开启接触 |
| 接触中移动 | `INRANGE \| INCONTACT \| UPDATE` | 每帧更新坐标 |
| 抬起 | `INRANGE \| UP` | **必须发**，否则触点永远挂着（曾经造成左键锁死事故） |

**几个关键坑（都是实测踩出来的）：**

1. **相邻两帧坐标必须变化**：完全相同坐标的 UPDATE 帧系统直接报 `err=87 (ERROR_INVALID_PARAMETER)`。之前我们把它误诊为「本机不支持触摸注入」而熔断——实际上只要跨度不变时给中心加 ±1px 交替微移就完全正常。
2. **帧内两触点必须同帧提交**：一次 `InjectTouchInput(2, arr)` 传两个 POINTER_TOUCH_INFO，frameId 相同，系统才认为是一帧多点。
3. **`historyCount` 必须为 1**（未合并历史时），0 在部分系统上被判无效参数。
4. 注入失败熔断要谨慎：连续失败 3 次才判定不支持，且失败计数在成功后归零。

### 两条路线的手感本质区别

| | 路线 A（Ctrl+滚轮） | 路线 B（触摸注入） |
|---|---|---|
| 缩放粒度 | 离散格，一格一跳 | 连续相对量，逐帧 |
| 手指停住 | 无手势概念，余量游走会造成画面乱动 | 手势保持活跃，画面静止 |
| 松手行为 | 每格都已刷新，无「定稿」 | 应用收 UP 才重排 → 模糊→清晰的定稿 |
| 应用兼容 | 全兼容 | 现代应用全支持，极老程序可能不认触摸 |

## 三、DrawTouch 的实现：手机当触摸板的全链路

### 3.1 总体架构

```
┌─────────── 手机端 (Kotlin) ───────────┐        ┌────────────── PC 端 (.NET 8) ──────────────┐
│ PenCanvasView 触摸事件                │  TCP   │ TcpPenServer 解析 TYPE_MOUSE 帧            │
│  → 双指手势状态机（捏合/滚动/跟随）    │ ─────→ │  → MOUSE_ZOOM: ①触摸注入(优先)             │
│  → 捏合: 算相对系数 factor            │  6000  │                ②Ctrl+滚轮(降级)            │
│  → MOUSE_ZOOM/MOUSE_SCROLL 帧        │        │  → MOUSE_FINGER off: EndTouchZoomIfActive  │
│  → MOUSE_FINGER 在板/离板状态帧       │        │ MouseControl: InjectTouchInput 状态机       │
└──────────────────────────────────────┘        └────────────────────────────────────────────┘
```

协议帧格式：`0x53 0x50 + type + len + payload`。触摸板动作全部走 `TYPE_MOUSE (0x07)`，payload 首字节是子命令 kind（`MOUSE_MOVE=0 … MOUSE_LEFT_DOUBLE=16`），后接两个 float（dx/dy，语义随 kind 变化）。`MOUSE_ZOOM` 的 dx 字段就是**相对缩放系数 factor**（>1 张开 / <1 捏拢）。

### 3.2 手机端：双指手势状态机（PenCanvasView.kt）

> **关键澄清：手机传的是语义指令，不是触点数据。**
> 经常被问：发给 PC 的是 `POINTER_TOUCH_INFO` 吗？是每个 pointer 的坐标吗？——都不是。
> `POINTER_TOUCH_INFO` 只存在于 PC 端内存，是 PC 收到指令后**现场合成**的。
> 手机发的是**语义指令**：「这是捏合，相对系数 ×1.03」「这是滚动，dy=35px」「这是双指点击」。
> 手势是什么、该干什么，在手机上就已经决定了。
>
> 为什么不在 PC 端算捏合系数？因为**「这是捏合还是滚动还是移动」的判定无论如何都要在某个地方做，而它只能做在有原始触点数据的那一端——手机**：
>
> 1. **PC 看不见两根手指。** 原始触点只存在于手机的触摸事件流里。要让 PC 判定，就得把两指原始坐标逐帧传过去——判定逻辑（捏合/滚动/单指跟随的消歧，即整个状态机）只是从手机搬到 PC，一点没少，还多了一层传输。
> 2. **Windows 不会替你消歧。** 就算把原始双指坐标原样注入，Windows 只把它们当「两个移动的触点」透传，应用会同时看到 pan 和 zoom 混叠：手指稍不完全平行，滚动就带出缩放抖动。真实触摸板的系统级手势合成是精密触摸板驱动栈的特权；`InjectTouchInput` 走触摸屏路径，没这层。手机端判定后发出的 factor 是**纯缩放**（只有跨度变化、中心不动），滚动是**纯滚动**——语义干净。
> 3. **相对系数才是本质信息，触点是布景。** 应用算缩放量只看**跨度的相对变化率**；PC 端的基准跨度 ±90px 是虚构的，绝对值无所谓。就算传了原始坐标，PC 最终能提取的有效信息也正是手机算的那个 factor。
> 4. **几何映射绕不开。** `InjectTouchInput` 要屏幕绝对坐标、触点不能出屏；手指在手机上的位移映射到桌面哪个虚拟区域、捏合中心放哪（= 光标位置），本来就得 PC 端重建。传原始坐标只是多一层要对齐的换算。
>
> 一句话：**手机端是手势翻译官，PC 端是手势演员**——翻译官决定这句话是什么意思，演员在系统面前把它演成一段标准、无噪声的双指触摸戏。

三态 + 一个锁存位：

- `tp2State`：0=未判定 → 1=缩放 / 2=滚动 / 3=单指跟随（光标移动）
- `tpPinchLatched`：捏合锁存，一旦判成捏合，**直到全部手指抬起前任何事件都不重置、不再发移动指令**——彻底隔离「缩放中混进光标移动」。

**判定优先级（每帧两指事件到达时）：**

1. **捏合随时可判、最优先**：`TwoFingerLogic.opposing()`——两指各自累计位移向量模都 ≥ `TP2_BOTH_MIN_DP=3dp`，且**点积 < 0**（在相反方向上运动）。点积判据的好处：不要求幅度相等（用户要求：「只要不是一个静止就算捏合」），也不要求精确共线；
2. **单指跟随 / 滚动**要等启动窗口 `TP2_FOLLOW_DELAY_MS=150ms`——给「捏合起手一指先动」留识别时间，防止把质心位移误判成滚动/移动；
3. 判成缩放后，跨度系数 `factor = span / lastSpan`，只有 `|factor-1| > PINCH_IDLE_DEADZONE=0.005` 才发帧——**手停死区**，防止停手微抖在 PC 端累积成随机游走。

**状态帧**：手指按下触摸板区域/离开时发 `MOUSE_FINGER(on/off)`——这是 PC 端精确结束捏合的信号源。

### 3.3 PC 端：缩放双路径 + keep-alive（MouseControl.cs / TcpPenServer.cs）

**MOUSE_ZOOM 到达时：**

```
① 触摸注入优先（_cfg.PinchMode != "Wheel" 且注入可用）
   UpdateTouchZoom(factor, 光标位置):
     首帧   → Down: 两触点落子 (cx±90, cy)，开启手势
     后续帧 → Move: span = clamp(span × factor, 24, 600)
              span 没变 → 中心 ±1px 交替微移（防 err=87，两帧抵消）
② 注入不可用 → 降级 Ctrl+滚轮：对数余量 _zoomNotch 累计，够一格发一格
```

**手势生命周期（对标真实触摸板的三件套）：**

| 真实触摸板行为 | 我们的对应实现 |
|---|---|
| 手指停住 → 手势仍活跃、不刷新 | `TZ_KEEPALIVE_MS=120`：手停时定时器注入 keep-alive 微移帧（坐标必变、跨度不变），应用始终看到「两指按着」 |
| 手指抬起 → UP 定稿、变清晰 | 手机 `MOUSE_FINGER off` → `EndTouchZoomIfActive()` 立即注入 `INRANGE\|UP` 帧，应用此刻才重排 |
| 异常兜底 | `TZ_SAFETY_LIFT_MS=3000`：3 秒完全无帧才强制抬手，防触点残留（曾经的左键锁死事故） |
| 系统不支持 | 连续失败 3 次熔断 → 永久降级 Ctrl+滚轮，不再刷日志 |

**语义指令 → PC 端系统调用对照（注意：没有任何一条传触点坐标）：**

| 手机端发的 kind | payload | PC 端动作 |
|---|---|---|
| `MOUSE_MOVE(0)` | 归一化位移 dx/dy | `SendInput` 鼠标相对移动（光标） |
| `MOUSE_ZOOM(6)` | 相对系数 factor | 合成两触点注入（`span×=factor`）或 Ctrl+滚轮 |
| `MOUSE_SCROLL(5)` | 滚动量 dx/dy | 像素级滚轮（非触摸注入——纯滚动不需要手势生命周期） |
| `MOUSE_FINGER(15)` | 在板/离板 | on：S Pen 让位；off：`EndTouchZoomIfActive()` 结束捏合定稿 |
| `MOUSE_LEFT_*` / 右键 / 中键等 | — | 对应鼠标按键合成 |

### 3.4 平移与滚动：横向 / 纵向 / 斜向各走什么 API（2026-11-01 定稿）

> 一句话：**双指平移默认走触摸注入（原生双指手势，系统翻译成各方向都能用的 pan）**；
> 备选是**同一组 `SendInput` 滚轮 API** —— 纵向 `MOUSEEVENTF_WHEEL`、横向 `MOUSEEVENTF_HWHEEL`、
> **斜向 = 两者在同一帧里各发一次**（没有、也不需要一个「斜向 API」）。
> 单指滚动**永远**走滚轮，与双指平移在两个不同的帧类型上（`MOUSE_SCROLL` vs `MOUSE_PAN`）。

#### 3.4.1 为什么要写这一节（错误猜测的代价）

最初横向/斜向平移走的是**触摸注入**，理由是代码注释里一句「OneNote 忽略横向滚轮 `WM_MOUSEHWHEEL`」——
那句话**从来没有证据**。后来写了受控探针 `tests/hwheel_probe.py` 实测：

```
SendInput(HWHEEL, +360) → 控件收到 WM_MOUSEHWHEEL，wParam = +360（同号），
                          横向滚动位置 0 → 90 → 180；再发 -720 → 回到 0
```

结论是横向滚轮**在系统层完全可用、方向也没反**。用户当时的原话「不是不会动，就是很慢」其实已经说明了它会动。
真正的毛病在别处：每帧位移被 `Math.Round` 后**不留残量**，慢速平移的 0.1~0.3px 帧帧被丢 → 位移攒不起来（详见 3.4.5）。

#### 3.4.2 手机端：方向在这里被判定，但**不决定 API**

`PenCanvasView.kt`：`scrollEmitter.feed(axis, dCx, dCy)`

| 方向 | 轴锁 `tpScrollAxis` | 输出 |
|---|---|---|
| 横向 | `AXIS_X` | 只出 `dx`，`dy` 归零 |
| 纵向 | `AXIS_Y` | 只出 `dy`，`dx` 归零 |
| 斜向 | `AXIS_FREE` | `dx`、`dy` **同时**输出 |

- 轴锁由 `TwoFingerLogic.decideAxisOrNull()` **只判一次**（已判定则不再改判；`AXIS_FREE` 一旦激活就全程全方向）。
- `ScrollEmitter` = `MoveDeadZone(catchUp=false)`：起手吃掉一个死区 `moveDeadZoneDp` 默认 **3dp**
  （density 1.8 → **5.4 逻辑像素**），越过后 **1:1 原样输出**——慢速位移一分不丢。
- 归一化后发出：`onMouse(MOUSE_PAN, -gate.dx / h * scrollScale, -gate.dy / h * scrollScale)`，
  `h` = 书写区高度（px）。
- **双指平移用专属帧 `MOUSE_PAN(17)`**（v4 起）。原因：`MOUSE_SCROLL(5)` 被另外三处复用
  ——单指滚动（滚轮条）、点击滚一格、手势滚——它们一律 `dx = 0`，与「纵向双指平移」在协议上
  完全同形。一旦把触摸注入挂到 `MOUSE_SCROLL` 上，**每次普通滚动都会起一个触摸手势**：
  光标被藏起来，而且列表 / 对话框 / 菜单只认滚轮、手势会被吞掉。分开帧之后，
  单指滚动**永远走滚轮**，只有 `MOUSE_PAN` 才可能走触摸注入。

#### 3.4.3 PC 端：`MOUSE_PAN` / `MOUSE_SCROLL` 共用一段代码，先决定「注入还是滚轮」

`TcpPenServer.cs`（`MOUSE_SCROLL`）→ `MouseControl.cs`：

```csharp
// 只有「双指平移帧」才可能走触摸注入；单指滚动永远走下面滚轮
if (kind == MOUSE_PAN && _cfg.IsTouchPan && MouseControl.TouchPanAvailable()
    && MouseControl.UpdateTouchPan(-pxX, -pxY))
    break;                                     // 成功走注入，本帧不再发滚轮

// ---- 滚轮路径（PanMode=Wheel / 注入不可用 / 单指滚动）----
double pxX =  dx * SCROLL_PIXELS_PER_SCREEN;   // 360：划满书写区高度 = 滚 360 单位
double pxY = -dy * SCROLL_PIXELS_PER_SCREEN;

_scrollRemX += pxX;  _scrollRemY += pxY;       // 亚像素残量累积（上限 ±400）
int stepX = (int)_scrollRemX;  _scrollRemX -= stepX;   // 截断取整，余数留下帧
int stepY = (int)_scrollRemY;  _scrollRemY -= stepY;

int v = PreciseDelta(stepY);   // 纵向
int h = PreciseDelta(stepX);   // 横向
if (v != 0) MouseControl.WheelPixels(v);    // → SendInput(MOUSEEVENTF_WHEEL,  v) → WM_MOUSEWHEEL
if (h != 0) MouseControl.HWheelPixels(h);   // → SendInput(MOUSEEVENTF_HWHEEL, h) → WM_MOUSEHWHEEL
```

| 方向 | 使用的 Windows API | 消息 | 备注 |
|---|---|---|---|
| **纵向** | `SendInput` `INPUT_MOUSE`，`dwFlags = MOUSEEVENTF_WHEEL(0x0800)`，`mouseData = v` | `WM_MOUSEWHEEL` | `v = -dy × 360`；手指上滑 → 内容向下（传统滚轮方向） |
| **横向** | `SendInput` `INPUT_MOUSE`，`dwFlags = MOUSEEVENTF_HWHEEL(0x1000)`，`mouseData = h` | `WM_MOUSEHWHEEL` | `h = +dx × 360`；手指右移 → 内容向左（触摸板自然方向） |
| **斜向** | 上面**两条在同一帧各发一次** | `WM_MOUSEWHEEL` + `WM_MOUSEHWHEEL` | 没有第三个 API；两轴分量各自独立累积残量 |

`PreciseDelta()` 的作用：把整数像素转成「**永远不会是 120 的整数倍**」的滚轮增量——
120 的倍数会被 Windows 当普通鼠标滚轮（一格一格跳），非整数倍才按高分辨率滚动（触摸板那样平滑）处理。

#### 3.4.4 默认方式：触摸注入平移（`PanMode = "Touch"`），以及「平移时鼠标照样能用」

`MouseControl.UpdateTouchPan()`：`CreateSyntheticPointerDevice` + `InjectSyntheticPointerInput`
注入**两个一起平移的触点**，由系统翻译成前台应用的原生平移手势。

- 坐标规则（实测，与缩放同源）：`注入值 = 全局坐标 − VirtualScreen.Left/Top`。
- 用户要求（2026-11-01）：**默认用触摸注入**，并且要像真实触摸板一样 ——
  **双指 pan 的同时，物理鼠标仍然可以自由移动光标**。

实现上踩过**三个坑**，每个都用受控探针/日志取证定位（`tests/PanProbe`、`tests/pan_cursor_wake_probe.py`、
`tests/pan_mouse_together.py`）：

| 现象 | 旧做法 | 取证结论 | 现在的做法 |
|---|---|---|---|
| pan 时鼠标动不了 | 每帧 `SetCursorPos` 钉回起点 + 8ms 看护定时器 | 注入接触期间系统**不会**把光标拽到触点（120 帧长平移偏移 **0px**）；接触期间鼠标通道**全速可用**（+80 米奇 → 339px，无接触时 338px） | 用户一动鼠标就**一个字节都不碰**（钩子判据），1:1 跟手 |
| pan 时指针消失 | 完全不叫醒（或只在抬手后叫醒） | 接触期间 `CURSOR_SHOWING=false`，且不会自己恢复；`SetCursorPos` 同点**无效**，只有「1 像素相对移动」能点亮 | 接触期间**按需点亮**（发现隐藏才戳） |
| **pan 时指针跟着手指跑、松手又弹回原位** | 点亮时 `atSaved:false`（以**当下光标位置**为准） | 系统在触摸接触期间会把光标「提升」到触点，`GetCursorPos` 读到的是**触点**；照着它点亮 = 把指针显示在手指上，松开接触点后系统撤销提升 → 指针又跳回起点 | 一律以**锚点**（平移起点）为准：偏差 >2px 就 `SetCursorPos` 钉回，点亮也钉在锚点；锚点只在用户动物理鼠标时跟到他真实位置 |

- **锚点（anchor）= 平移开始时的光标位置**，是本轮平移期间「光标应该待在哪」的唯一真相。
  平移的每一次更新都会 `GetCursorPos` 比对：偏离 >2px 即钉回，日志打
  `[TouchPan] 系统把光标提升到触点 → 钉回锚点 偏差 Npx … 钉回后(x,y) 仍偏差=M`，
  用于判断「钉回到底生不生效」。
- **锚点什么时候更新**：只有当**用户自己**在动物理鼠标时才跟着走（否则用户松手 250ms 后
  我们会把他刚挪过去的光标拽回平移起点 = 抢鼠标）。锚点值取**钩子事件里的坐标**
  （`MSLLHOOKSTRUCT.pt`），不取「当下 `GetCursorPos`」——后者可能已被触摸提升污染成触点。
- **怎么判断「用户自己在动鼠标」**：低级鼠标钩子 `WH_MOUSE_LL`。这里有两个被证伪的宽判据：

  | 判据 | 结果 |
  |---|---|
  | 「光标位置变了 = 用户动了」 | ✗ 触摸提升自己就会改位置；而且桌面窗口上注入 120 帧偏移 0px、真实应用窗口上出现过 19~39px，同样的情况两种表现 |
  | 「`dwExtraInfo != 0` = 外部注入 = 用户」 | ✗ **触摸提升的合成事件是 `flags=0x1(INJECTED) extra=0xFF5157F2`**，会被当成用户动作。实测后果：一轮平移 32 次把锚点跟到触点 → 指针跟着手指跑 **109px** |
  | 「`LLMHF_INJECTED == 0` 才是物理鼠标」 | ✓ 采用。另外放行测试脚本专用的 `dwExtraInfo = 0x54455354('TEST')`，产品路径不依赖它 |

- 点亮策略：用户最后一次**物理**鼠标动作 < **250ms** → 一个字节都不碰光标（系统自己会显示它）；
  超过 250ms 且发现光标隐藏 → 戳一下；单次没戳亮 **40ms** 后立刻重试，
  连续 3 次失败才退避 **400ms**（一次失败就退避会让斜向隐藏采样从 2% 恶化到 40%）。
- 抬手后走尾巴期看护：**钉回锚点**（锚点已跟随用户鼠标，所以不会抢）并点亮，
  而不是「以当下位置为准」——抬手那一刻读到的是触点位置，会把指针显示在手指附近（= 松手弹一下）。
- 自检口径（`tests/pan_mouse_together.py`）：

  | 场景 | 期望 |
  |---|---|
  | 全程不动鼠标 | 光标位移 **0px**、日志「光标离开锚点最大 ≤3px」、锚点未被跟随 |
  | 边平移边动鼠标 | 光标确实被推动（实测 +180px）、日志「锚点位移 180px / 锚点被跟随 12 次」、抬手后不拽回 |

**两种方式都给用户留着**（滚轮仍是一等公民，也是注入不可用时的兜底）。切换入口三处，改任意一处立即生效：

| 入口 | 位置 | 作用范围 |
|---|---|---|
| 手机端设置页 | 设置 →「指针与滚动」→ **双指平移方式**（触摸注入 = 默认 / 滚轮） | 保存在手机 `prefs` 的 `panMode`，**每次连接随握手帧下发** |
| PC 端配置窗体 | 「双指平移方式」下拉 | 写进 `appsettings.json` 的 `PanMode`，作为 PC 端默认值 |
| 配置文件 | `appsettings.json` 的 `"PanMode": "Touch" \| "Wheel"` | 同上 |

- 协议：握手帧 `TYPE_HELLO` 的**第 9 个 float**（offset 32）= `panMode`（`0=Wheel` / `1=Touch`），
  payload 32→36 字节（`PROTO_VER` 2→3）；v4 又新增了 `MOUSE_PAN(17)` 帧（`PROTO_VER` 3→4）。
  **两端必须同步**，否则黄灯拒绝对接。老的 32 字节 HELLO 不带该字段 → PC 保留自己配置里的值。
- 切换时 PC 会清理另一条路径的残留：`EndTouchPanIfActive()`（注入的接触点不能挂着）
  + `_scrollRemX/Y = 0`（滚轮残量不能让切回滚轮后的第一帧突然跳一下）。
- 选了「触摸注入」但本机创建不了合成指针设备（远程桌面 / 部分虚拟机 / 权限不足）时，
  PC 打一条节流警告并**回退为滚轮**，而不是装死。
- 取证脚本：`tests/pan_mouse_together.py`（平移时鼠标能不能同时动）、
  `tests/pan_mode_switch.py`（握手帧能不能真的改路径）。

#### 3.4.5 最小步长（经实测，不是推断）

链路上的最小量：`起手死区 5.4px` → `每 1 个滚轮单位需手指移动 h/360 px`
（h≈593 → 约 **1.65px/单位**）→ **`1 单位 = 1/120 格**（`WHEEL_DELTA = 120`）**。
从静止到第一次滚动 ≈ **7px（≈3.9dp）**；之后每 ~1.65px 输出 1 单位。

但「发出去」≠「内容动了」。受控探针 `tests/wheel_granularity_probe.py`（自建多行 EDIT，读首个可见行）实测：

| 注入 delta | 内容变化 |
|---|---|
| 1 / 2 / 3 / 4 / 8 / 15 / 30 | **+0 行**（子格增量被控件整条丢弃） |
| 60 / 119 / 120 | 各 **+3 行**（约半格起跳成整格） |
| 连发 20 次 delta = -1 | **仍 +0 行**（不累积） |

⇒ 标准 Win32 控件吃不住子格增量；能按高分辨率滚轮累积的应用（OneNote 已确认可用）才吃得住。
我们这一侧**位移不丢**（残量累积 + 截断取整），丢不丢在应用自己的取整方式。

### 3.5 多显示器坐标处理（2026-10-31 定稿）

这一节回答一件事：**一块以上的显示器时，所有坐标各自属于哪套坐标系、怎么换算、边界怎么夹。**
下面每条都标了代码出处；带「实测」的是跑出来验证过的，其余是代码事实，未实测的会明说。

#### 3.5.1 唯一基准：虚拟屏幕（所有显示器的合并包围盒）

`MappingConfig.ResolveVirtualScreen()`（`MappingConfig.cs:129`）取四个系统度量：

```
VirtualX = GetSystemMetrics(76)   // SM_XVIRTUALSCREEN
VirtualY = GetSystemMetrics(77)   // SM_YVIRTUALSCREEN
VirtualW = GetSystemMetrics(78)   // SM_CXVIRTUALSCREEN
VirtualH = GetSystemMetrics(79)   // SM_CYVIRTUALSCREEN
```

关键性质：**原点可以是负数**（显示器排在左/上方时），宽高是能包住所有屏的矩形。
所以「副屏在左边」不是特例，只要全程用虚拟屏幕基准，负坐标天然就对了。
回退：宽高读到 0（老系统/无多屏支持）时退到 `SM_CXSCREEN(0)/SM_CYSCREEN(1)`。

之后所有东西——操作框、笔的坐标、鼠标移动、画布位图——**都以这个盒子为基准**，
不再出现「第几块屏」的概念。这是整个多屏方案的地基。

#### 3.5.2 前提：进程必须是 PerMonitorV2 DPI 感知

`Program.cs:41-53`，三级降级：

```csharp
Application.SetHighDpiMode(HighDpiMode.PerMonitorV2)          // 首选
  → SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)
  → SetProcessDPIAware()
```

**为什么这是前提（实测）**：同一个进程不感知时 `GetSystemMetrics` 返回虚拟化尺寸 ——
本机实测不感知读 `1755×1097`、感知后读 `3072×1920`。差的就是那个缩放倍率（175%）。
坐标映射会整体错位一个倍率，副屏上尤其明显。

**坑**：不能自己先 P/Invoke 设感知就让 WinForms 跑 —— 那样 WinForms 仍按 SystemAware 布局，
窗口被系统按 96/168 缩小、文字仍按 168DPI 渲染，结果是「窗口很小、内容全被裁掉」
（`Program.cs:45-47` 注释，用户截图就是这个问题）。必须让 `SetHighDpiMode` 统一接管。

**分层窗口还要多做两步**（`HighlighterOverlay.cs`）：

| 处理 | 位置 | 原因 |
|---|---|---|
| `AutoScaleMode = AutoScaleMode.None` | :449 | `Form.Bounds` 用逻辑像素，画布/光标用物理像素，两者混用窗口位置会被缩放偏 → 笔迹画到画布外（等于没画） |
| `WndProc` 里 `if (m.Msg == WM_DPICHANGED) return;` | :490-493 | 窗口跨到不同缩放的屏时系统会发这个消息，WinForms 默认按建议值改窗口大小和位置 → 窗口被拽走，坐标系对不上 |

#### 3.5.3 三套坐标系的换算表（核心）

| 用途 | 坐标系 | 换算 |
|---|---|---|
| 读光标、夹取、框位置 | **虚拟屏幕全局坐标**（物理像素） | `GetCursorPos` 直接给，原样用 |
| 光标**绝对**移动 `SendInput` | 归一化到虚拟桌面的 0..65535 | `Norm(v,origin,size) = round(clamp((v−origin)/size,0,1) × 65535)`（`MouseControl.cs:1202`），配 `MOUSEEVENTF_ABSOLUTE \| MOUSEEVENTF_VIRTUALDESKTOP` |
| **触摸注入** `ptPixelLocation` | **相对虚拟桌面原点的局部坐标** | `注入值 = 全局坐标 − (VirtualScreen.Left, VirtualScreen.Top)` |

第三行是踩过最狠的一个坑，实测钉死（`MouseControl.cs:152-170` 注释 + `TryPrepareTouchZoomTarget`）：

```
实测（本机虚拟桌面 X=-1920 Y=0）：注入 2625 → 全局 705；注入 120 → 全局 -1800（都精确命中）
旧代码把全局坐标当注入值 → 副屏上注入 -1200 被解释成 -3120 → 越界
  → 被 Windows 夹到主屏右沿 → 光标被系统直接拖走（用户报的「指针消失、飞到主屏右侧」）
```

> 另有一种等价写法：`ptPixelLocation` 按 `hwndTarget` 所在显示器原点解释。
> 这跟上面的 `−VirtualScreen.Left/Top` 是同一物理事实的两种表述，**以本表为准**，别当成两条冲突规则。

绝对移动**必须**带 `MOUSEEVENTF_VIRTUALDESKTOP(0x4000)`：不带的话坐标按主屏解释，负坐标那块屏根本到不了。

#### 3.5.4 显示器级约束：跨度上限按「光标所在那块屏」算

光有虚拟屏幕不够 —— 两个触点必须都落在**同一块显示器**上，所以上限要按那块屏算：

```csharp
// TryPrepareTouchZoomTarget：MonitorFromPoint(p, MONITOR_DEFAULTTONEAREST) → rcMonitor
int spanLimit = Math.Min(gx - mon.Left, mon.Right - gx) - TZ_EDGE_MARGIN;   // TZ_EDGE_MARGIN = 8
_tzMaxSpan = Math.Min(TZ_MAX_SPAN /*900*/, Math.Max(TZ_MIN_SPAN, spanLimit));
```
（`MouseControl.cs:985-988`）

**为什么不能用虚拟桌面算**：会算出横跨到隔壁屏的跨度 → 触点出屏 → 系统把光标拽到出界后的落点，
这正是「光标飞走」的帮凶之一。

顺带一条避坑（PC 端目前不需要找主屏，测试脚本需要）：要判「哪块是主屏」时，
用 `EnumDisplayMonitors` 找带 `MONITORINFOF_PRIMARY` 的那一块
（`tests/pinch_cursor_check.py:82-99`、`tests/pan_cursor_check.py:77-93` 就是这么做的），
**不要**用 `MonitorFromWindow(GetDesktopWindow(), MONITOR_DEFAULTTOPRIMARY)` ——
桌面窗口横跨所有显示器，返回的是交集最大的那块，不是主屏。

#### 3.5.5 操作框（映射区）跨屏：平移 / 缩放 / 夹取

| 操作 | 位置 | 算法 |
|---|---|---|
| 基准矩形 | `BaseRect()` `:210` | 按手机比例在映射区内等比留边（Keep），Stretch 时铺满 |
| 生效矩形 | `GetActiveRect()` `:251` | `BaseRect + FrameL/FrameT × 基准尺寸`，最后夹进 `[VirtualX, VirtualX+VirtualW−w]` |
| 夹取 | `ClampFrame()` `:271` | 由「框尺寸 vs 虚拟屏幕」**反推** `FrameL/FrameT` 的上下限 |
| 归一化 → 像素 | `ToPixels()` `:347` | 先 clamp(0..1) → 框内像素 → 再夹虚拟屏幕 |
| 鼠标模式 | `ToPixelsFull()` `:365` | 直接铺满整块虚拟屏，不留边、不平移 |

两个要点：

- `ClampFrame` 的上下限是**从虚拟屏幕推出来的**，不是手机端那种 `[0, 1−Scale]` 的书写区相对量。
  这样手指滑动平移时不会「撞到隐形墙」出现死区，框也能被拖到第二块屏上。
- 范围框 `RegionFrame.cs:94` 直接 `Bounds = new Rectangle(r.x, r.y, r.w, r.h)` —— 负坐标 Win32 原样接受，不需要额外换算。

#### 3.5.6 显示器热插拔：虚拟屏幕会变，必须复查

`RefreshVirtualScreenIfChanged(nowMs)`（`MappingConfig.cs:162`）：

- 最多每 **500ms** 复查一次 `GetSystemMetrics(76..79)`（`GetSystemMetrics` 很便宜，但没必要每帧调）；
- 变了就 `ResolveVirtualScreen()` + `ClampFrame()` + 触发 `Changed`（重画框），并记日志
  `[Display] 虚拟屏幕变化：旧值 → 新值`。

**为什么必须**：以前只在启动时取一次，插拔第二屏 / 改分辨率 / 接远程桌面之后映射区域就变成过期的旧值 ——
光标被夹在过期范围里（表现为「完全控制不了」），桌面框和笔的落点也跟着错（笔明明在框里却没反应）。

画布类同样要跟着变：`ResizeToVirtualScreen()` → `SyncBounds()` → `RebuildCanvas()`
（`HighlighterOverlay.cs:497-532`）按新虚拟屏尺寸重建位图（物理像素），并重新对齐窗口位置。

#### 3.5.7 光标移动的「读回 + 残量」机制（系统可能截断你的移动）

`MoveBy()`（`MouseControl.cs:344-387`）不是「发出去就完事」，而是**发完立刻读回真实位置**：

```
目标 = clamp(光标 + 位移, 虚拟屏幕范围)
   ↓ SendInput(绝对 + VIRTUALDESKTOP)
GetCursorPos 读回 q
   ├ q 一点没动  → 退回「相对移动」Send(MOUSEEVENTF_MOVE, dx, dy) 再验一次
   │               仍不动 → InputGuard.NoteCursorStuck()（这是 UIPI/权限问题，不是坐标问题）
   └ q 走了一部分 → 返回残量 (tx−q.X, ty−q.Y)
```

残量由调用方攒着下一帧继续走（`TcpPenServer.cs:826-841`，上限 `MoveRemainLimit = 600`）。
绝对定位会被系统改写/拒绝的场景：Windows 虚拟桌面（每个桌面有自己的显示器布局）、异构多屏/缩放不同的屏。

还有一个边界特判（`:352-354`）：光标已经贴着屏幕边、这一帧本来就推不动时
**不能**据此判定注入失败 —— 以前没这条，指针停在角落会误报「注入被权限拦截」。

#### 3.5.8 分层窗口的内容推送：画布 = 整块虚拟屏的位图

`HighlighterOverlay.PushRegion`（`:780-806`）：

- **DIB 画布 = 虚拟屏幕大小**（不是窗口大小），脏区按**绝对偏移**拷进去；
- `UpdateLayeredWindow` 传 `ptSrc = 脏区偏移`、`ptDst = 虚拟屏原点 + 脏区坐标`、`size = 脏区尺寸`；
- **不用窗口矩形反推**：窗口万一被挪动，内容仍落在正确的屏幕区域；
- **也不要指望 `pptDst + psize` 缩放**：本机实测 `UpdateLayeredWindow` 只挪位置不缩放窗口
  （传了 pptDst+psize 后 `GetWindowRect` 位置对、尺寸仍是旧值）。

#### 3.5.9 实测拓扑快照（以及为什么测试不能写死坐标）

| 时间 | 实测内容（DPI-aware 物理坐标） |
|---|---|
| 2026-10-31 双屏在线 | 主屏 `(0,0)-(3072,1920)` primary；副屏在**左侧** `(-3840,-248)-(0,1912)` |
| 2026-10-31 23:2x（副屏已断开） | 只剩主屏 `(0,0)-(3072,1920)`，`SM_XVIRTUALSCREEN = (0,0,3072,1920)` |

> 双屏在线时的虚拟盒子 `(-3840,-248,6912×2168)` 是由上面两块矩形**推出**的，
> 当时没有直接读 `SM_XVIRTUALSCREEN` 核对，故标注为「推导」而非「实测」。

结论很实在：**同一台机器一天之内拓扑就变过**，所以任何写死 `(-1200,900)` 之类坐标的测试都会失效。
正确做法是运行时 `EnumDisplayMonitors` 动态枚举、取每块屏的矩形中心当测试点 ——
`tests/pinch_cursor_check.py`、`tests/pan_cursor_check.py` 就是这么做的（无副屏时自动跳过该屏用例）。

### 3.6 当前与真实触摸板的差距（诚实清单)

1. **接触矩形是假的**：注入的 rcContact 固定 ±3px，没有真实手指的接触面积/压力变化。对缩放手感无影响，但依赖接触面积的少数应用（如压感绘画）会感知差异。
2. **±1px jitter 理论可感知**：同坐标防 87 的微移在数学上两帧抵消，但逐帧看中心在 ±1px 摆动，极少数对亚像素敏感的应用可能察觉极轻微抖动。
3. **keep-alive 帧率 8Hz**：真实触摸板手停时也在 125Hz+ 刷新（只是位移为零）。我们的 keep-alive 是 120ms 一帧——对「保持手势活跃」这个目的足够，但不是物理等价。
4. **触摸注入 ≠ HID 驱动级设备**：注入的触摸来自「虚拟触摸屏」而非「虚拟触摸板」，系统层某些触摸板专属特性（如三指手势、边缘滑动）不会由系统自动合成。我们的做法是手机端识别手势后映射成具体动作（音量、Alt+Tab 等已是这个思路）。
5. **终极方案（未做）**：写一个虚拟 HID 精密触摸板驱动（内核级），让系统把手机当成原生 PTP 硬件——兼容性和系统合成手势都是满血，但需要驱动签名，工程量大，暂不划算。

## 附录：一次捏合的完整数值实例

场景：手机 1080×2340，PC 2560×1440，用户在 OneNote 里双指张开放大画布。

**① 手机端 · 触摸事件流（原始双指坐标，每 16ms 一帧，从不上网）**

```kotlin
MotionEvent(
  pointer0: (620.3, 815.2) px,   // 食指
  pointer1: (705.8, 830.1) px,   // 拇指
  action = MOVE                    // 两指都按在触摸板区
)
```

**② 手机端 · 状态机判定（每帧一次）**

```kotlin
tpVecA = (12.4, -3.1) px    // 食指累计位移，向右上
tpVecB = (-14.8, 2.9) px    // 拇指累计位移，向左下

TwoFingerLogic.opposing()：
  magA = 12.8 ≥ 3dp门槛 ✓
  magB = 15.1 ≥ 3dp门槛 ✓
  点积 = 12.4×(-14.8) + (-3.1)×2.9 = -192.5 < 0（反向）✓
→ 判成捏合：tp2State=1，tpPinchLatched=true（从此不再发光标移动）
```

**③ 手机端 · 相对系数 + 死区过滤**

```kotlin
span_last = 185.6 px; span_now = 191.2 px
factor = 191.2 / 185.6 = 1.0302
|1.0302-1| = 0.0302 > PINCH_IDLE_DEADZONE(0.005) ✓ 发帧
（若算出 1.003 → ≤ 死区 → 本帧丢弃，什么都不发）
```

**④ 网线上实际跑的字节（全部有效信息 = 4 字节）**

```
53 50 07 0D 06 | D8 DD 83 3F | 00 00 00 00
│  │  │  │  │    └ dx = 1.0302（float32 小端）＝相对缩放系数
│  │  │  │  └ kind = 0x06 = MOUSE_ZOOM
│  │  │  └ payload 长度 = 13
│  │  └ type = 0x07 = TYPE_MOUSE
│  └ 魔数 'P'   └ 魔数 'S'
没有坐标、没有 pointer、没有触点。
```

**⑤ PC 端 · TcpPenServer 解析**

```
kind=6 → MOUSE_ZOOM，factor=1.0302
GetCursorPos() → (1247, 633)   // 捏合中心 = 光标位置
```

**⑥ PC 端 · MouseControl 合成触点（触点在此诞生）**

```
首帧：pointerId=0 坐标(1157,633)，pointerId=1 坐标(1337,633)
      = 中心(1247,633) ± 90；rcContact ±3px
      flags = INRANGE|INCONTACT|DOWN，frameId=1；span 记 90
后续帧：span = 90×1.0302 = 92.7 → 93
      pointerId=0 (1154,633)，pointerId=1 (1340,633)
      flags = INRANGE|INCONTACT|UPDATE，frameId=7
InjectTouchInput(2, contacts) → true
```

**⑦ 系统 → 应用（应用收到的是这些）**

```
win32k 合成 pointer 帧 → OneNote 同帧收到两个 WM_POINTERUPDATE
DirectManipulation 算触点间距 186/180 ≈ ×1.03
→ 画布拉伸 3%（位图插值、模糊），不重排
```

**⑧ 手停（keep-alive）**

```
手机端死区滤帧 → 网线安静。
PC 端每 120ms 注入一帧：span 仍 93（不变），中心 ±1px 交替：
  (1246,633) → (1248,633) → (1246,633)…  flags=UPDATE
应用看到「两指按着、没动」→ 手势继续挂着 → 不刷新、不居中。
```

**⑨ 松手定稿**

```
手机发：53 50 07 0D 0F | 00 00 80 3F …（kind=0x0F=MOUSE_FINGER，离板）
PC 端 EndTouchZoomIfActive() 注入：flags = INRANGE|UP
→ OneNote 收到两个 WM_POINTERUP → 手势终结 → 重排 → 变清晰
```

**兜底支线**：第⑥步连续失败 3 次（err=87）→ 永久熔断，改走 Ctrl+滚轮：
`_zoomNotch += ln(1.0302)×10 = 0.297 格`，累计满 1 格才发 `Ctrl+滚轮 ±1` —— 离散跳变、每格刷新的老路。

## 四、一页速查

- **真实触摸板**：硬件报原始触点 → Windows 统一成 WM_POINTER 流 → 应用直接操作；流畅的根源 = 连续相对量 + 手势生命周期与手指绑定（松手才定稿）。
- **模拟路线**：SendInput 滚轮（离散、必刷新）vs InjectTouchInput 触摸注入（连续、可保持手势）——我们选后者，滚轮作降级。
- **我们的链路**：手机端状态机（opposing 向量判捏合 → 锁存隔离 → 死区滤抖）→ TCP 帧携带相对 factor → PC 端触摸注入状态机（Down/Move/Up 严格状态机 + keep-alive 手停保持 + MOUSE_FINGER off 精确结束 + 3s 兜底 + 失败熔断降级）。
- **平移/滚动（横·纵·斜）是另一条路，且只有一条**：手机端按 `dx/dy` 归一化 → 一个 `MOUSE_SCROLL` 帧 → PC 端亚像素残量累积 + 截断取整 →
  **纵向 `SendInput(MOUSEEVENTF_WHEEL)`、横向 `SendInput(MOUSEEVENTF_HWHEEL)`、斜向 = 两者同帧各发一次**。
  `PanMode = "Touch"` 的触摸注入分支保留但**默认关闭**（触摸接触期间系统会隐藏光标，与「横向要和纵向一样」的要求冲突）。
- **滚轮的最小步长是 1 单位 = 1/120 格**，且「发出去」不等于「内容动了」——标准控件会整条丢弃子格增量且不累积（实测见 3.4.5）。
- **多屏坐标只有一套基准：虚拟屏幕**（`SM_XVIRTUALSCREEN`，原点可为负）。三套换算：读光标/夹取用全局物理坐标；
  绝对移动用 `MOUSEEVENTF_VIRTUALDESKTOP` + 归一化 0..65535；**触摸注入用「全局 − VirtualScreen.Left/Top」**（传错会让光标飞走）。
  跨度上限按**光标所在那块屏**算；进程必须 PerMonitorV2 DPI 感知，否则整体错位一个缩放倍率（详见 3.5）。
- **调试入口**：PC 日志 `[TouchZoom]` 前缀（开始捏合/注入失败/捏合结束）、`[Mouse] 捏合 ×… → 触摸板真实缩放 | Ctrl+滚轮 N 格`。
